# TeleMotoMax

Клиент моста для Motorola V3 — форк Jimm 0.6 (исходники проекта Jimm,
GPL-2, см. `COPYING`). Работает с мостом по обычному OSCAR, как любой Jimm,
но объявляет мосту собственную способность (`TMM:` + версия в 02/04), и мост
отдаёт такой сессии расширения протокола, которых обычный Jimm не поймёт.
Обычный Jimm при этом работает с мостом как раньше — расширения включаются
только для сессии, в которой они объявлены.

Сборка — из исходников рядом, ничего в систему не ставится (JDK 8, Ant,
ProGuard 4.11 и заглушки CLDC/MIDP скачиваются в рабочий каталог):

```sh
telemotomax/build.sh ~/tmm-build              # результат в ~/tmm-build/out/
telemotomax/build.sh ~/tmm-build "TMM test"   # под другим именем — рядом с обычным
```

Версия — в файле `VERSION`, и она одна на всё. Сборка сама проставляет её
в `MIDlet-Version` (по нему телефон отличает сборки при установке), пишет
`TeleMotoMax-Version` с датой сборки (`0.3.260916` — это и видно в «О
программе») и подставляет старший с младшим номером в способность, которой
клиент представляется мосту. Поэтому в журнале моста при входе — ровно та
версия, что стоит на телефоне:

```
клиент 91.78.159.86:63668: TeleMotoMax 0.3 — расширенный протокол
```

## Чем отличается от Jimm

Модули: у V3 — `SMILES_STD`, `AVATARS` (и вариант Light без смайлов), у V8
— `SMILES_STD`, `AVATARS`, `CAMERA`;
только русский язык; без значков меню и
заставки (с мостом не нужны, а в куче телефона занимали ~125 КБ); без
модуля `FILES` и регистрации UIN — вырезаны из исходников (см. ниже);
ProGuard 4.11 — с 6.2 KVM Motorola сборку не запускает.

Правки в коде (относительно Jimm 0.6.091219):

- **История и запись голоса (с 1.16).** На V3 и Light серверная история
  держит до 384 строк и 16 КБ исходного текста; длинная отдельная запись
  ограничена 48 строками с видимым многоточием. «Ещё» загружает до 10
  сообщений, вытесняя уже просмотренный новый хвост. Номера страниц,
  вложения, обсуждения и ссылки для цитирования сохраняются. Вложенное
  обсуждение освобождает страницу родителя; «Назад» заново запрашивает
  историю около выбранного сообщения. На V8 пределы больше: 1024 строки,
  32 КБ текста, до 20 сообщений в пачке и 96 строк на сообщение.
  Запись голоса хранится блоками по 2 КБ, отправляется без полной копии и
  освобождается по мере отправки. Предел рассчитывается при открытии
  микрофона: половина свободной кучи после резерва 48 КБ, максимум 512 КБ.
  Он проверяется при записи каждого блока; при достижении запись завершается.
- **Восстановление после отказов (с 1.16).** Отказ отправки сохраняет черновик
  и редактор; исходящая строка появляется только после принятия в очередь.
  Отказ создания потока переподключения освобождает запрет новой попытки и
  повторяет её через минуту с помощью уже имеющихся часов. Отказ потока
  истории оставляет возможность повторить запрос. Выход из истории отменяет
  BART-запрос и освобождает его части. Ошибка следующей страницы «Все чаты»
  сохраняет прежний список и повторяет тот же номер страницы. При сбоях
  подготовки микрофона плеер закрывается; раннее или повторное нажатие
  «Стоп» отправляет одну запись. Таймаут цитирования работает при молчании
  сервера. Поиск оставляет одно поле названия чата и добавление по UIN;
  отмена не открывает прежние семь полей ICQ. Статусы ищут контакты по
  компактному индексу без повторного обхода контакт-листа.
  Неиспользуемые названия языков исключены из русского пакета, исправлен
  отсутствовавший перевод схемы WA Bento. Сообщения моста о начале и конце
  набора текста доступны на DEBUG. `config.toml` менять не нужно.
- **Работа при нехватке памяти (с 1.15).** Очередь интерфейса ограничена
  64 событиями и 16 КБ текстов и пакетов; один большой пакет допускается
  отдельно. Обработка идёт по 16 событий, без копии всей очереди.
  Повторные тики часов объединяются, дата форматируется раз в минуту.
  «Все чаты» загружаются страницами по 20 записей и разбираются по четыре
  за один вызов интерфейса. Кэш переписки ограничен 12 окнами, включая
  непрочитанные: значок непрочитанного сохраняется, текст вытесненного окна
  снова запрашивается при открытии. После выхода из раздела настроек
  освобождаются ссылки на его поля и списки. Некорректные числа не сохраняют
  часть формы; старый нулевой интервал пингов заменяется на 120 секунд.
- **Отмена и параллельные запросы (с 1.15).** Правая софт-клавиша отменяет
  подключение и во время открытия сокета. Поздний результат старой попытки
  закрывается, не затрагивая новый сеанс. Служебные запросы используют одно
  соединение; ошибка одного не закрывает его для остальных. Обрыв внутри
  пакета вызывает обработку потери связи, таймауты проверяются и при полном
  молчании сервера. Подтверждение отправки медиа проверяется по чату, операции
  и сеансу; отменённая отправка не продолжается после переподключения.
  Отложенный возврат из медиа выполняется через очередь интерфейса и
  сохраняет экран блокировки с PIN. Фото и аватарки декодируются по очереди,
  освобождая поток связи. Пинг и ошибка звукового плеера при нехватке памяти
  не останавливают общий таймер. На V8 записанное видео отправляется из файла
  частями; загрузки сохраняются через собственный временный файл, существующий
  файл получает соседнее имя (`photo-1.jpg`), отмена не удаляет чужую загрузку.
  `config.toml` менять не нужно. Повторяющиеся строки моста про количество
  чатов и приметы аватарок перенесены из INFO в DEBUG.
- **Порог пингов (с 1.14).** В «Настройки → Сеть → Пингов без ответа»
  выбирается от 1 до 10, по умолчанию 3. После последнего пинга клиент
  ждёт ещё один интервал; любые данные от моста сбрасывают счётчик.
  Настройка сохраняется и применяется со следующей проверки связи,
  без переподключения и дополнительного таймера.
- **Последнее сообщение и недоступная сеть (с 1.14).** Пустой чат просит
  последнее сообщение при открытии и после неудачной загрузки допускает
  повтор при следующем открытии. Пока запрос выполняется, повторы не
  добавляются. Ответ проверяется по чату, номеру запроса и уникальной
  примете; закрытие, повторное открытие и переподключение не позволяют
  старому ответу попасть в новый чат. Пришедшее живое сообщение имеет
  приоритет. Ошибка истории видна в открытом чате, фоновая ошибка не
  переключает экран. «Невидимый» означает недоступную сеть: его значок
  остаётся, но контакт не входит в онлайн-счётчики и сортируется с
  оффлайном. «Скрывать отключившихся» скрывает его по тем же правилам,
  сохраняя открытые чаты. Обычный оффлайн собеседника позволяет загрузить
  историю, если сама сеть доступна. Изменения общие для V3, Light и V8;
  `config.toml` менять не нужно.
- **Плеер без служебных потоков (с 1.13).** Ожидание медиа, время
  голосового и поддержание подсветки используют общий таймер приложения.
  Задача ставит не больше одного вызова в очередь интерфейса. Голосовое
  обновляет время раз в секунду; при паузе, после окончания и на скрытом
  экране лишней перерисовки нет. При «Назад» задача отпускает экран;
  запоздалая подготовка закрывает свой плеер. Каждое открытие получает
  отдельный временный файл, поэтому старый загрузчик не удалит файл нового.
  Нехватка памяти при подготовке закрывает нативный плеер, а сбой задачи
  времени не останавливает общий таймер. Изменения общие для V3, Light и V8;
  `config.toml` менять не нужно.
- **Разбор текста без временных буферов (с 1.12).** Смайлы ищутся за один
  проход по исходному сообщению, по группам первого символа и короткому
  префиксу. Нет копии всего текста в нижнем регистре, списка кандидатов
  и массива на каждое найденное совпадение. Сохраняются регистр подписи,
  картинки и приоритет длинных вариантов. Проверка наличия ссылки для
  меню не собирает список адресов; скрытая ссылка видео проверяется в
  исходном тексте без копирования подписи. Добавлено распознавание HTTPS
  и `ftp://`, ссылки разных типов сохраняют порядок в сообщении, конечный
  перевод строки или кавычка не попадают в адрес. Пустое действие перехода
  по ссылке безопасно закрывается. Изменения общие для V3, Light и V8;
  Light по-прежнему собирается без смайлов. `config.toml` менять не нужно.
- **Имена отправителей вне списка (с 1.20).** Входящее сообщение от чата
  или контакта, не вошедшего в выданный телефону список, сразу показывает
  его имя. Мост передаёт название из своей базы вместе с первым фрагментом
  сообщения; это работает для Telegram, MAX, eXpress, вложений и
  офлайн-пачки. Клиент применяет имя до создания чата и подписи сообщения,
  а уже открытый чат с номером вместо имени переименовывает на месте.
  Используются обычные временные контакты. Название ограничено настройкой
  `bridge.alias_max_chars` и 64 символами; метаданные учитываются в пределе
  памяти очереди и освобождаются после обработки. Дополнительных запросов
  профиля, потоков и записей в RMS нет. Имена, уже заданные в списке или
  вручную, сохраняются. Повреждённое имя не мешает доставить текст.
  Нужно обновить мост и клиент; `config.toml` менять не требуется.
  Формат включается только для TeleMotoMax 1.20+, обычный Jimm и прежние
  версии сохраняют совместимость. Проверки:
  `tests/test_contact_names.py` и `tests/test_client_contact_names.py`.
- **Доставка и прочтение (с 1.11).** Текстовое сообщение с телефона получает одну
  галочку после успешной отправки в сеть и двойную после её подтверждения
  прочтения. Поддержаны события Telegram, MAX и eXpress. В Telegram первая
  галочка означает приём облаком Telegram. Для функций используется
  существующий переключатель в настройках сообщений, теперь он называется
  «Доставка и прочтение»; его сохранённое значение остаётся прежним.
  Прочтение хранится в уже существующих битах метаданных, для отложенного
  сообщения — в байте вместо прежнего булева признака доставки. На каждое
  сообщение не добавляется объект или поле. Двойная галочка собирается из
  прежнего рисунка один раз при первом прочтении, сохраняет размер и
  прозрачность; временный массив пикселей не удерживается. Запоздалая
  доставка не понижает прочтение, входящее сообщение с совпавшим ID
  не меняется. Отметки для закрытого чата применяются при его открытии;
  закрытые и вытесненные сообщения не восстанавливаются по подтверждению.
  Мост учитывает раннее прочтение во время RPC отправки и прочтение при
  переподключении; кэши ограничены 200 записями. Для темы форума подтверждение
  общего peer передаётся её UIN. Обновить нужно мост и клиент, `config.toml`
  менять не нужно. С прежним мостом остаётся одна галочка по его `ack_on`;
  обычный Jimm и клиент до 1.11 также сохраняют эту прежнюю схему.
- **Вставка скопированного текста (с 1.3).** «Копировать» сохраняет текст
  сообщения во внутреннем буфере приложения. В редакторе нового сообщения
  появляется «Вставить»: текст добавляется в позицию курсора, сохраняя
  черновик. Если места в редакторе не хватает, клиент показывает ошибку
  и сохраняет и черновик, и буфер. Для штатной пересылки с вложениями
  используйте «Цитировать → Цитировать сюда».
- **Автоблокировка при простое (с 1.2).** В «Настройки → Интерфейс»
  отдельное числовое поле «Автоблокировка, мин»: по умолчанию 2 минуты,
  0 выключает её, доступны значения до 999 минут. При обновлении прежней
  версии также включаются 2 минуты. Проверка выполняется в очереди
  интерфейса существующим десятисекундным обновлением часов; блокировка
  срабатывает на ближайшем обработанном обновлении после срока простоя.
  Нажатие, удержание и отпускание клавиши обновляют время активности.
  Редакторы сообщений, формы, окна ошибок, подключение и экраны медиа
  приостанавливают отсчёт; возврат в обычный экран и разблокировка начинают
  его заново. Используется прежняя блокировка, PIN и профили оповещений.
  С 1.21 удалены пробная диагностика флипа из 1.18 и попытка фоновой
  автоблокировки из 1.17: проверка на телефоне их не подтвердила.
  Автоблокировка при закрытой крышке не гарантируется. Изменения общие
  для V3, Light и V8; `config.toml` не нужен.
- **Запуск без ожидания отрисовки (с 1.19).** Обновление «Загрузки» и
  прогресса подключения запрашивает асинхронную отрисовку: поток запуска
  не ждёт выполнения `paint`. Это исправление сохранено в 1.21.
  Проверка `tests/test_client_lock.py` запускает `ClientStartupTest` на
  реальном `SplashCanvas`, проверяя одновременную отрисовку, остановленную
  очередь отрисовки и её возврат. Она входит в проверки V3, Light и V8.
- **Два независимых списка вибрации (с 1.0).** В «Настройки → Оповещения»
  для обычного режима и блокировки можно выбрать «Нет» или длительность:
  0,1 / 0,2 / 0,5 / 1 / 1,5 / 2 секунды. Общий переключатель условий
  удалён; при новой установке оба списка стоят на «Нет». При обновлении
  прежние «Нет», «Да» и «Если заблокирован» переносятся в соответствующие
  профили, а «Если не трогали 60 с» становится вибрацией при блокировке.
  Заданные в 0.98–0.99 длительности сохраняются; у более старых версий
  используется прежняя длительность 0,5 секунды. «Нет» пропускает вызов
  вибромотора, остальные варианты запускаются одним вызовом
  MIDP `Display.vibrate`, без дополнительного таймера и потока; сообщения
  в открытом чате и подавленные повторные уведомления по-прежнему её
  не запускают. С 1.1 вариант 0,05 секунды удалён: на V3 он не работает,
  поэтому сохранённые 0,05 с заменяются на 0,1 с. Изменения общие для V3,
  Light и V8; `config.toml` не нужен.
- **PIN и компактные оповещения (с 0.97).** В «Настройки → Интерфейс»
  можно задать PIN блокировки из 4–8 цифр; пустое поле выключает его.
  С 1.4 экран блокировки сразу предлагает ввод PIN: цифры скрыты,
  правильный код автоматически разблокирует приложение после последней
  цифры, без `#`. Неверный код очищается с подсказкой для повторного ввода.
  `*` стирает последнюю цифру, правая софт-клавиша очищает ввод.
  Без PIN остаётся прежняя разблокировка удержанием `#`.
  Переподключение и окна ошибок сохраняют блокировку с PIN. Ввод использует
  один массив из 8 символов, который создаётся при первой цифре и очищается
  при выходе или уходе в фон; отдельная форма и таймер PIN не нужны.
  В «Оповещениях» режим и мелодия объединены в один выпадающий список
  на каждый профиль: «Нет», «Писк» или имя файла. Для «печатает» сохранён
  режим «Только оповещение». Громкость каждого профиля остаётся отдельной.
  Настройки 0.95–0.96 сохраняются; PIN по умолчанию выключен. Собраны V3,
  Light и V8; `config.toml` менять не нужно.
- **Два профиля звука сообщений (с 0.95).** В «Настройки → Оповещения»
  обычный режим и блокировка приложения имеют отдельные режим, громкость
  и мелодию. Вместо ввода имени файла — выпадающий список `message.mp3`,
  `msg_low.mp3`, `tg.mp3`, `typing.mp3`; такой же список у звука «печатает».
  По умолчанию в обычном режиме выбран `msg_low.mp3`: исходный звук
  сообщения обработан фильтром `volume=1/20` и сохранён как MP3 (с 0.99;
  в 0.96–0.98 использовалось `volume=1/12`). При
  блокировке остаётся прежний `message.mp3`. При обновлении сохраняются
  прежние громкость и режим, включая отключённый звук, а новая мелодия
  обычного режима становится тихой. Удалены уведомление о подключившемся
  контакте, его настройки и файлы `online.*`. Изменения общие для V3,
  Light и V8; `config.toml` менять не нужно.
- **Серверная история без повторного переноса (с 0.94).** «Ещё» разбивает
  на строки только новую страницу и добавляет её перед уже готовыми
  строками. Полный текст сообщений больше не хранится вторым списком:
  остаются строки экрана, токены вложений, номера для цитирования,
  обсуждения и скрытые ссылки видео. Типы вложений хранятся в байтах,
  без `Integer` на каждое сообщение. История из одного BART-пакета
  читается прямо из его массива. Ограничение в 200 сообщений действует
  и на размер последней страницы. Ошибка разбора или нехватка памяти
  при новой странице сохраняет уже открытые сообщения и возможность
  повторить запрос. «Назад» освобождает все данные истории, запоздалый
  ответ её не открывает. Изменения общие для V3, Light и V8;
  `config.toml` менять не нужно.
- **Меньше выделений памяти (с 0.93).** Числовые ключи переводов хранятся
  в массиве без отдельных строк-ключей и узлов `Hashtable`. Перенос строк
  измеряет участки исходного текста без временных подстрок; длинное слово
  разбивается двоичным поиском. События интерфейса поступают одной пачкой
  без повторного копирования их параметров. Фото из одного пакета и
  аватарки декодируются прямо из тела ответа; перед новой аватаркой
  освобождается предыдущая. Таймеры анимации, аватарок и звука создаются
  при первом использовании. Убраны пустые для моста интересы ICQ,
  неиспользуемые классы `ErrorPacket` и `PingPacket` и консольный вывод
  отладочного журнала в обычных сборках. Журнал «Связь» сохранён.
  Шифрование использует меньший рабочий массив SHA-256; отменённый
  таймер согласования сразу отпускает ссылку на сокет. Изменения общие
  для V3, Light и V8; `config.toml` менять не нужно.
- **Память для фото (с 0.92).** Перед декодированием фото освобождаются
  кеш аватарок и ссылки на них в карточке контакта. Очистка аватарки по
  таймеру также убирает её из карточки, сохраняя текст; при следующем
  открытии аватарка запрашивается заново. Декодирование фото выполняется
  по одному, чтобы закрытый экран не создавал вторую картинку одновременно
  с новым. При `OutOfMemoryError` после сборки мусора делается одна повторная
  попытка. Журнал «Связь» показывает размеры JPEG, свободную память до и
  после очистки и сообщение декодера. Это снижает расход памяти, но не
  гарантирует открытие любого JPEG на конкретной прошивке телефона.
- **Причины отказа фото (с 0.91).** Экран различает ошибку загрузки,
  нехватку памяти и отказ JPEG-декодера. Перед декодированием запускается
  сборка мусора, чтобы освободить временные буферы пакетов и согласования
  шифрования. Ошибка службы, согласования или таймаут показывается с причиной.
  В «О программе → Связь» записываются размер полученного JPEG, свободная
  память и результат открытия. Переподключение телефона сохраняет токены
  вложений на мосту (24 часа); перезапуск моста их сбрасывает.
- **Выход из настроек (с 0.90).** «Назад» в общем списке настроек явно
  закрывает этот экран перед возвратом. Если приложение ушло в фон между
  нажатием и обработкой команды, настройки больше не открываются повторно.
  После сохранения или отмены «Сети» выход возвращает на предыдущий экран;
  «Назад» внутри раздела по-прежнему возвращает к списку настроек.
- **Удобный ввод ключа (с 0.89).** В «Настройки → Сеть → Ключ / кодовая фраза»
  можно ввести от 1 до 64 символов, включая короткий цифровой код, русские
  буквы и пробелы. В `[oscar].psk` задаётся тот же текст; обновить нужно
  и мост, и клиент. Регистр и внутренние пробелы учитываются, пробелы по
  краям убираются. Старые ключи из 64 hex-знаков сохраняют прежнее значение.
  Короткий код легче подобрать, чем длинную фразу.
- **Шифрование по запросу клиента (с 0.88).** В «Настройки → Сеть» добавлены
  «Шифровать соединение» и поле ключа. По умолчанию выключено.
  Один и тот же ключ задаётся на телефоне и в `[oscar].psk`.
  Защищаются все сокеты приложения: авторизация, основной и BART; обычные
  клиенты ICQ работают без изменения. Неверный ключ или отказ моста
  показываются как ошибка подключения, без автоматического открытого входа.
- **Выпадающие списки медиа (с 0.87).** Все списки в «Настройки → Медиа»,
  включая поворот фото и видео, открываются как «Часовой пояс».
  Сохраняются доступные варианты и выбранные значения; «Ролик в памяти,
  КБ» остаётся числовым полем.
- **Ошибки серверной истории (с 0.86).** При сбое загрузки клиент
  показывает ошибку вместо «Сообщений нет». Для ограничения частоты
  запросов мост передаёт пояснение и время ожидания, если сеть его сообщила.
  Уже открытые сообщения остаются на экране; после ошибки подгрузки можно
  повторить «Ещё». Мост запрашивает ручную историю MAX с `interactive=true`,
  включая открытие чата, `!last`, `!render` и `!lastfoto`; фоновая догрузка
  использует обычную квоту. Старый клиент показывает общую ошибку загрузки.
- **Цитирование через мост (с 0.85).** На нужном сообщении выберите
  «Цитировать», перейдите в целевой чат и выберите «Цитировать сюда».
  Мост штатно пересылает исходное сообщение с автором и вложениями
  внутри Telegram, MAX или eXpress; текст в буфер телефона не копируется.
  Выбирать можно новые сообщения, свои отправленные сообщения и строки
  серверной истории. После успеха выбор сбрасывается; при ошибке его
  можно повторить. Повторное нажатие во время отправки не создаёт вторую
  пересылку. Между Telegram, MAX и eXpress мост отправляет текст с заголовком
  «Цитировано из Telegram, чат „Название“:» (или MAX/eXpress), получив полный
  текст и оригинальные вложения с сервера исходной сети. Фото, видео,
  голосовые и файлы переносятся без телефонного перекодирования. В eXpress
  голосовое из другой сети отправляется аудиофайлом. Длинный текст идёт
  несколькими сообщениями, с заголовком у каждого; если он не помещается
  в подпись, медиа отправляется отдельно с тем же заголовком.
  Мост сначала скачивает все вложения, проверяя их суммарный размер по
  `[render].source_max_mb`. При ошибке скачивания ничего не отправляет,
  а клиент показывает ошибку. Ограничения штатной пересылки сохраняются.
  Нужны обновлённые мост и клиент, а для старых сообщений, оставшихся
  на телефоне без номера, откройте серверную историю. Новые параметры
  `config.toml` не требуются, база обновляется автоматически.
  Для пересылки между сетями достаточно обновить мост; клиент 0.85 подходит.
- **Убраны неработающие функции ICQ (с 0.84).** Удалены HTTP-транспорт,
  поля User-Agent/WAP-профиля и выбор типа подключения из телефонных
  сборок: мосту подключаемся по сокету. Открытие ссылок, фото и видео по
  HTTP сохранено. Удалены запрос текста статуса, его горячая клавиша и
  автоответы; обычный статус по-прежнему выбирается в главном меню.
  Распознавание QIP, Miranda и остальных клиентов удалено вместе с
  таблицами имён и версий. Способности протокола для сообщений, UTF-8,
  аватарок и «печатает» сохранены.
- **Поиск без неработающих фильтров (с 0.84).** Удалены возраст, пол и
  «только онлайн» из формы и поискового пакета: мост их не учитывает.
  Поиск чатов по тексту и номеру сохранён.
- **Непрозрачное меню (с 0.84).** Удалены настройка «Прозрачность» и
  полупрозрачная отрисовка меню и курсора с отдельным буфером пикселей.
  Меню и курсор всегда непрозрачные, как при прежнем значении «Нет».
- **Без сохранённой последней ошибки (с 0.84).** Из «О программе» убран
  блок «Последняя ошибка», удалено его хранение в RMS. Журнал связи и
  защита возврата из фона с переходом в главное меню сохранены.
  Старые параметры удалённых функций отбрасываются при загрузке; их
  номера в RMS не переиспользуются. Назначенная ранее горячая клавиша
  запроса статуса сбрасывается в «Нет», остальные назначения сохраняются.
  Изменения общие для V3, Light и V8; `config.toml` менять не нужно.
- **Подключение на весь экран (с 0.83).** Надпись «Отмена» скрыта,
  правая софт-клавиша отменяет текущий вход. Удержание и повторное
  нажатие после завершения входа его повторно не отменяют.
- **Обычный статус — в главном меню (с 0.83).** Убраны настройки
  «Статус», «Доп. статус», «Автомат. статус», «X-Статусы» и «Иконки
  клиентов». Удалены редакторы, хранение описаний статусов, автостатус
  с таймером, обработка X-статусов и код с картинками иконок клиентов.
  Ручное переключение обычных статусов сохранено; пауза в работе
  приложения больше не меняет выбранный статус. Старые параметры
  удалённых функций при загрузке настроек отбрасываются, остальные
  настройки и учётная запись сохраняются. Изменения общие для V3,
  Light и V8; `config.toml` менять не нужно.
- **Без старой анкеты и отправки журнала (с 0.83).** Убраны «Мои
  данные» с редактором анкеты ICQ и пункт «Журнал связи в чат» с его
  обработчиком отправки. Карточки контактов и просмотр событий связи
  в «О программе» сохранены.
- **Не больше 12 открытых чатов в памяти.** В Jimm каждое входящее
  сообщение открывает чат, который живёт со всем текстом, пока его не закроют
  руками. При открытии нового чата сверх двенадцати закрывается самый старый
  без непрочитанных и не на экране.
- **Аватарки у контактов не в сети.** Уход контакта в офлайн стирал примету
  аватарки; теперь она живёт, пока сервер не пришлёт новую.
- **Аватарка в карточке с первого раза.** Jimm вставлял картинку в
  открытую карточку из потока связи раньше, чем главный поток успевал её
  сохранить, — при первом открытии индикатор доходил до конца, а картинки не
  было; теперь карточка обновляется после сохранения.
- **Аватарки не копятся в памяти.** Jimm держал каждую полученную картинку до
  перезахода (160×160 — это ~100 КБ кучи за штуку). Теперь в памяти только
  последняя, и та отпускается через 30 секунд; контакт при этом забывает, что
  картинка получена, и при следующем открытии карточки запрашивает её снова.
- **Сторож связи.** Мост отвечает на каждый keepalive, и если в ответ на
  выбранное число пингов подряд не пришло ни байта, клиент считает канал потерянным и
  переподключается. Оборванное на GPRS соединение остаётся открытым:
  телефон показывал бы «в сети», ничего при этом не получая.
- **Плееры не текут.** У Motorola число плееров на приложение ограничено,
  и каждая неудачная попытка открыть камеру, микрофон или проиграть запись
  оставляла плеер незакрытым — через несколько попыток «MediaException:
  too many players», и не работали уже ни камера, ни микрофон до
  перезапуска. Теперь плеер закрывается на любой неудаче; плеер
  уведомления, если телефон не сообщил конец звука, закрывается сторожем
  через 8 секунд.
- **«Информация» о контакте с аватаркой.** Контакт, загруженный из
  записи телефона (сервер ответил «список не менялся»), оставался без
  примет аватарки — `null` вместо массивов; «Информация» падала с
  `NullPointerException` в потоке интерфейса, и пункт меню просто не
  срабатывал. Загруженный контакт теперь получает те же поля, что и
  контакт из полного списка, а по «не менялся» помечаются открытые чаты.
- **Сообщение из одного символа.** Jimm берёт текст расширенного
  сообщения только при длине больше байта — рассчитывая на завершающий
  ноль, который мост не слал. «1» от бота молча пропадала и уходила
  заново через 10 минут. Мост теперь шлёт ноль, как сам Jimm; клиент
  принимает и без него.
- **Очередь действий не запирается.** У Jimm действие, которое к моменту
  запуска стало невыполнимым (второй `ConnectAction` после удавшегося
  входа), оставалось в голове очереди навсегда — фото, история, голосовые
  после этого не начинались. Такое действие теперь снимается с ошибкой.
  Переподключение назначается одно: два обрыва подряд (сторож пингов и
  приёмник сокета) давали два потока, два входа и как раз такой
  застрявший `ConnectAction`. Ручное «Отключиться» отменяет задачу
  keepalive сеанса — иначе после «Подключиться» пинги шли от двух задач.
- **Один вход и один таймер пингов (с 0.76).** Повторное «Подключиться»
  во время автоматического или ручного входа пропускается. Отключение
  отменяет запуск даже до создания сокета; каждый поток при выходе
  отменяет свой keepalive. Таймер отправляет через соединение своего
  сеанса и не меняет сторож следующего входа после задержавшейся отправки.
- **`OutOfMemoryError` — это обрыв, а не тишина.** Главный цикл и приёмник
  ловили только `Exception`; нехватка памяти на большом кадре убивала
  поток молча — сокет открыт, клиент «в сети», а читать некому. Теперь
  любой `Throwable` в них — ошибка связи с переподключением.
- **Голосовое ждёт до четырёх минут.** Мост сначала перекодирует, потом
  отдаёт частями; минутного срока на GPRS не хватало, и запрос считался
  пропавшим, когда первая часть ещё ехала.
- **Фоновая картинка — главный тормоз.** Фон (Интерфейс → фоновое
  изображение) рисуется заново при каждой перерисовке, а «мозаикой» —
  сотнями `drawImage` маленькой плитки на кадр: на V3 это сотни
  миллисекунд, и навигация по списку и меню становится вялой. Держите фон
  выключенным.
- **Кадр контакт-листа дешевле.** Замер на V3 показал 300–500 мс на
  перерисовку восьми строк и 150 мс на обработку клавиши. Причины были
  не в рисовании: высота каждой строки считалась через полную сборку
  элемента (текст, картинки, цвет) по нескольку раз за кадр; полоска меню
  копировалась попиксельно через `drawRGB`; каждое чтение настройки
  создавало `Integer`; разбор клавиши шёл через `getKeyName` и
  сравнения строк на каждое нажатие; текст группы со счётчиками склеивался
  заново при каждом обращении. Теперь высота строки дерева постоянная,
  меню рисуется полосами `fillRect`, ключи настроек и разбор клавиш
  кэшируются, текст группы пересобирается только при смене счётчиков.
- **Закрытые чаты не верстаются.** Сообщение в чат, которого нет на
  экране, раньше сразу раскладывалось по строкам: поиск смайлов по всему
  тексту и промер каждого слова шрифтом — в потоке интерфейса, десятки
  миллисекунд на сообщение на V3. В оживлённых группах это шло
  непрерывно и делало навигацию по контакт-листу вялой. Теперь такие
  сообщения откладываются и верстаются при открытии чата (текущий чат —
  сразу). Повтор клавиши при удержании не ставится в очередь, пока экран
  не перерисовался, — курсор больше не «доезжает» после отпускания.
- **Переподключение не сдаётся.** У Jimm на переподключение отведено
  число попыток (Сеть → 10 по умолчанию) с паузой 5 секунд; без сети они
  кончались за минуту, и клиент показывал ошибку и лежал «отключён», пока
  не нажмёшь «Подключиться». На GPRS обрыв на несколько минут — метро,
  лифт, перерегистрация — обычное дело. Теперь после быстрых попыток
  клиент продолжает пробовать раз в минуту (на заставке «ждём сеть»),
  пока не подключится или пока не отключат руками. Ошибка показывается
  только там, где повтор бессмыслен: неверный пароль, вход с другого
  устройства и подобное. И переподключение **тихое**: у Jimm каждая
  попытка показывала заставку «Подключение…» с командой «Отмена» —
  открыл телефон, нажал клавишу, попал в отмену, а отмена у Jimm значит
  «отключился руками»: автоматика выключалась насовсем, и клиент лежал
  «отключён» до ручного «Подключиться». Теперь попытка идёт без заставки
  (только мини-индикатор на списке), отменить её нечем, а по успеху экран
  не дёргается, если открыт чат. Ошибка старой, зависшей в `Connector.open`
  попытки не рвёт новую (у Jimm она била по общему соединению), а если
  сама попытка не смогла начаться (нет памяти, не создался поток) — повтор
  через минуту, а не тихий конец цепочки. В «О программе» — журнал «Связь»:
  последние восемь событий с временем (обрыв, решение, попытка, успех,
  отключение руками), чтобы «лежит отключённый» разбирался по фактам.
- **Служебное соединение не копится.** За аватарками, фото, историей и
  голосовыми клиент ходит вторым сокетом. В Jimm он никогда не закрывался
  при ошибке или таймауте (код рассчитывает на `onEvent(ON_ERROR)`, который
  главный цикл не вызывает), а новый открывался поверх старого — брошенные
  сокеты копились, пока телефон не отказывал в новом: «Неизвестная ошибка
  (#100.51)». Теперь сокет закрывается при любой неудаче, перед открытием
  следующего и если им не пользовались две минуты (мост закрывает своё
  через три, и на GPRS его FIN до телефона может не дойти). В ошибке
  показывается настоящий код (#120 — ввод-вывод, #121 — сеть не даёт
  соединение), а не безликое #100.
- **Подсветка не гаснет, пока идут части и пока идёт ролик.** Ролик, голосовое или файл по
  GPRS — минуты, и телефон, лежащий на столе, гасил экран; теперь приход
  каждой части (и отправка каждой части снимка, кружка, файла) будит
  подсветку — `Display.flashBacklight` на время из настройки подсветки, —
  На экране при этом видно, сколько принято: «Загрузка видео 2/4,
  48/120 КБ» (весь объём мост не присылает, но части, кроме последней,
  одного размера — значит по первой он известен; то же у «Скачать
  файл»), а на время проигрывания ролика подсветка подновляется каждые
  четыре секунды:
  клавиш во время просмотра никто не нажимает, и телефон гасил экран на
  середине. С 1.13 побудка плеера идёт через общий таймер и очередь
  интерфейса, без отдельного потока. Скрытый экран плеера подсветку
  не включает. Подготовка файла и плеера остаётся в рабочем потоке,
  чтобы не задерживать связь и интерфейс.
- **Фото и плеер не закрываются от любой клавиши.** Закрывают «выбор»
  («5»), «0» и «Назад»; остальные клавиши только будят подсветку — на V3 она
  гаснет быстро, и нажатие «чтобы увидеть» роняло картинку.
- **Поток связи не ждёт службу.** В Jimm второе соединение открывалось
  прямо в потоке связи: `Connector.open` на GPRS занимает секунды, а то и
  десятки, и всё это время не ходили ни сообщения, ни пинги. Теперь оно
  открывается в своём потоке. Заодно убраны две гонки, ронявшие главный
  цикл с #141 при живом сокете (после чего клиент показывал «в сети», но
  ничего не получал): обнуление служебного соединения из потока-приёмника
  и закрытие потока вывода во время отправки. Сбой главного цикла теперь
  считается обрывом связи — сокет закрывается и идёт переподключение, а не
  тихое зависание.
- **«Загрузка...» при уже отданном фото.** Две причины, обе убраны. Запрос
  аватарки в Jimm съедал любой ответ службы — в том числе фото, видео или
  голосовое для другого запроса: тот ждал до таймаута, а снимок становился
  аватаркой контакта; при этом на «аватарки нет» действие не завершалось и
  ещё минуту перехватывало чужое. Теперь аватарка берёт только свой ответ
  (по типу и хешу) и завершается по ошибке службы. Вторая — в главном цикле
  проверка «есть ли что читать» и ожидание шли под разными замками: пакет,
  пришедший между ними, никого не будил, и ответ службы лежал в очереди до
  следующего пакета основного соединения.
- **Одна мелодия на пачку.** После входа мост отдаёт накопившееся, и
  каждое сообщение звенело и вибрировало отдельно. Теперь в первые 20
  секунд после входа мелодия и вибрация — один раз, а в обычное время
  сообщения, пришедшие в пределах двух секунд, сливаются в одно
  оповещение.
- **Тишина в открытом чате.** Сообщение в чат, который на экране и в котором
  нажимали клавиши в последние 20 секунд, приходит без звука и вибрации.
- **Ролик боком** (Настройки → **Медиа** → «Ролик боком»: авто / всегда / никогда)
  и точно так же **«Фото боком»** для снимков и кадров-превью: те же флаги в
  запросе приметы (0x20 всегда, 0x10 никогда), в «авто» мост кладёт боком
  широкий снимок, если экран телефона портретный; поворот — в ту же
  сторону, что у ролика.
  При ручном повороте телефон при просмотре поворачивают. H.263 при
  этом сохраняет стандартный кадр 176×144 и не заменяется на MPEG-4.
  «Авто» — мост смотрит на исходник (`ffprobe`, с учётом тега поворота):
  широкий — боком, если профиль включает поворот; по умолчанию он выключен,
  в том числе у V8. Портретный и кружок — как есть. Выбор уходит мосту во
  флагах запроса ролика (0x20 всегда, 0x10 никогда); кадр и включение
  поворота — в профиле телефона (`video_width/height`, `video_rotate`).
- **«Свернуть»** в главном меню — уйти в фон, не закрывая соединение:
  `Display.setCurrent(null)` плюс `notifyPaused()`, какой из способов
  телефон понимает, тот и сработает; вернуться — из списка приложений,
  `startApp()` покажет экран. В JAD стоят `Background: True` и
  `FlipInsensitive: True` (моторольские директивы, разрешающие фон и
  продолжение работы при закрытии крышки). `pauseApp()` соединение не рвёт; в журнале «Связь» видно
  «свёрнуто», «pauseApp: в фоне», «развёрнуто» — по ним понятно, что
  именно делает телефон.
- **Своя способность `TMM:`** для опознания мостом.

## Закрытие крышки V3/V3r

В 1.21 удалены `FlipWatch` и фоновые изменения автоблокировки из 1.17–1.18.
Детектор выводил положение крышки из задержек таймера и обработчиков
интерфейса; сигнал датчика крышки он не получал. Пользователь проверил его
на V3r и сообщил, что определение флипа и блокировка при закрытии не работают.
Прежние утверждения о проверенных `hideNotify`, `pauseApp` и `isShown`
удалены: подтверждённых измерений этих вызовов на телефоне нет.

В [руководстве Motorola V300/V400/V500/V600, раздел Flip Behaviors](https://firmware.center/firmware/Motorola/V400%20%28Triplets%29/Product%20Info/Motorola_V300_V400_V500_V600_J2ME_Developer_Guide_v1_2.pdf)
атрибут `FlipInsensitive` выбирает приостановку приложения (`false`) или
продолжение работы (`true`) при закрытии крышки. В нашем JAD и манифесте
остаётся `True`; атрибут не возвращает состояние датчика. Этот документ
описывает другие модели и не устанавливает поведение очереди интерфейса
конкретной прошивки V3r.

После уточнения версии телефона разобран образ **R4515_G_08.BD.B3R**
с Java-пакетом `JAVA_G_08_R4515DI_06_00_04R` из
[архива прошивок V3r](https://firmware.center/firmware/Motorola/RAZR%20V3r%20(Razor%2005,%20V3_05,%20V3_CR)/Flash%20Files/MFFT,%20PST,%20RSD%20Lite/R4515_G_08.BD.B3R/).
Это статический разбор образа: региональные настройки конкретного телефона
и выполнение callbacks на самом аппарате он не измеряет.

В этом образе установлено следующее:

- Из ROM восстановлена полная таблица из 1169 Java-классов и 12030
  записей имён/сигнатур. Пакета `com.motorola.secondarydisplay` в ней нет.
  Наличие Secondary Display API в общем Motorola SDK 3.0 не означает
  наличие этого API на B3R.
- Внутренний `com.motorola.synerj.svc.device.Case.getFlipState()` существует
  и читает состояние крышки. Но инициализатор класса вызывает
  `SecurityManager.checkPermission()`. Проверка отличает системную Java VM
  от пользовательской и бросает **NoClassDefFoundError** в пользовательской
  VM. Этот путь нельзя использовать в обычном TeleMotoMax; добавление
  разрешения в JAD не заменяет системную VM.
- Есть другой путь: `com.vodafone.system.DeviceControl.getDeviceState(7)`.
  В нативном обработчике селектор `7` читает аппаратное состояние крышки.
  Путь не содержит проверки SynerJ, но зависит от системного флага `0x352`:
  при недоступности возвращается `-1`, и Java-обёртка бросает
  `RuntimeException`. Наличие метода в ROM ещё не доказывает его доступность
  при настройках установленной прошивки.
- В Vodafone API есть `BodyOpenListener.bodyOpened()/bodyClosed()` и
  обработка `EVENT_FLIP_STATE_CHANGED`. Это отдельные события платформы,
  не задержки очереди отрисовки. Их поступление обычному MIDlet с
  `FlipInsensitive: True` пока требует проверки на телефоне.
- Штатный `java.util.Timer` имеет нативный `waitResume()` и отдельный поток
  пробуждения таймеров. Поэтому работа сетевого потока сама по себе не
  подтверждает работу `TimerTask`. Этот факт не устанавливает, что именно
  остановилось в TeleMotoMax при закрытии крышки.

Связь классов, методов и проверки доступа можно повторно проверить
[inspect_firmware.py](../tools/motorola_flip_probe/inspect_firmware.py).
Он только читает SBF, проверяет SHA-256 и обходит ROM-таблицы. Образ в Git
не добавляется; инструмент не подключается к телефону и не прошивает его.
Поддерживается снимок
`R4515_G_08.BD.B3R_PDS007_LP0039_DRM0101_JPJAVA_G_08_R4515DI_06_00_04R_SE6763AXXB1140_1FF.sbf`
с SHA-256 `ad3052fc4d352b121d5c7c7f7097050942a5bb208c1a800f8eb5e211607d8b07`.

```sh
python3 tools/motorola_flip_probe/inspect_firmware.py /path/to/firmware.sbf
```

Для измерений подготовлено **отдельное** приложение `TMM Flip Probe`:
[исходники](../tools/motorola_flip_probe/FlipProbe.java) и
[сборка](../tools/motorola_flip_probe/build.py). Оно использует те же
`Background: True` и `FlipInsensitive: True`, но не меняет TeleMotoMax и
не блокирует экран. Раз в секунду проверяет прямой Vodafone API, отдельно
регистрирует события крышки, считает `Thread.sleep`, `TimerTask`,
`callSerially`, `paint`, `isShown`, `showNotify/hideNotify`, `startApp/pauseApp`.
Отсутствие API или ошибка записываются явно. По задержкам положение крышки
не вычисляется.

```sh
# Использует JDK 8, MIDP/CLDC и ProGuard 4.11 из существующего каталога сборки.
# Если каталога ещё нет: sh telemotomax/build.sh /tmp/tmm-build
python3 tools/motorola_flip_probe/build.py \
  --toolchain /tmp/tmm-build --output telemotomax/dist
```

Поставить `TmmFlipProbe.jad` как отдельную программу и запустить. Оставить
крышку открытой на 30 секунд, закрыть на 60 секунд, открыть, подождать
10 секунд и выбрать **«Закончить»**. Пункт сохраняет и показывает журнал;
после перезапуска его можно открыть через **«Прошлый журнал»**. Для сравнения
повторить опыт, оставив телефон открытым, но свернув программу в фон.
Нужны строки прямого API/`BodyOpenListener` и счётчики до/после закрытия.

В памяти хранится кольцо из 96 коротких записей; каждые пять секунд
сохраняется снимок счётчиков, отдельно — изменения и задержки. Запись в RMS
выполняется только при «Закончить»; во время опыта нет сети и записи на
флешку. Программа измеряет поведение небольшого MIDlet и сама по себе
не воспроизводит загрузку TeleMotoMax. Сборка и преверификация проверены,
работа на V3r ещё не проверена.

[MIDP Display.callSerially](https://docs.oracle.com/javame/config/cldc/ref-impl/midp2.0/jsr118/javax/microedition/lcdui/Display.html)
связывает вызов с очередью событий и циклом отрисовки, не с датчиком крышки.
Привязывать автоблокировку к API можно после подтверждения его доступности
и реальных переходов состояния. При недоступности API задержки интерфейса
не становятся достоверным показанием датчика.

## Что с памятью

Куча на V3 невелика, поэтому клиент старается не держать лишнего:

- Ролик и голосовое идут во временный файл по частям, как приходят:
  писатель в своём потоке дописывает каждую часть и после последней
  запускает плеер. Не требуется собирать весь клип в одном массиве.
  Пока запись не успевает за сетью, полученные части остаются в очереди
  в памяти. Без записываемого корня вложение собирается в памяти,
  как раньше; список чатов и история также хранятся в куче.
- Приёмник читает тело кадра сразу в кадр, а не через промежуточный
  массив: минус ещё одна копия части на каждый принятый пакет.
- Снимок и раскодированная картинка живут, пока открыт их экран.
- Открытых чатов в памяти не больше двенадцати: самый старый без
  непрочитанного закрывается сам.
- В каждом чате не больше 15 сообщений (настройка «Сообщений в чате»,
  Сообщения → рядом с числом сообщений истории): с приходом нового самое
  старое уходит из памяти. В Jimm предела не было —
  группа или канал, открытые входящим, копили всё подряд до закрытия
  чата руками, а каждое сообщение лежит в куче разложенным по словам;
  за день это и съедало кучу. За старым — «История с сервера».
- История с сервера держит не больше 200 сообщений и уносит их с экраном.
  С 0.94 полный текст не хранится вторым списком рядом со строками экрана.
- Звук «печатает» играет один раз за набор, а не на каждое уведомление
  от моста.

**Что вырезано ради кучи.** На KVM код лежит в той же куче, что и
данные, поэтому лишний класс — это не только байты в JAR. Из исходников
убраны целиком: модуль `FILES` (передача файлов и прямые соединения
между клиентами ICQ — с мостом не нужны), регистрация UIN и старые
настройки «фон из файла» и «способ передачи файлов». Для V3 есть ещё
сборка **Light** без `SMILES_STD`: ICQ-смайлы `:-)` в переписке из
Telegram/MAX — редкость, а набор картинок держит ~32 КБ кучи и
просматривает каждое сообщение. Итог: JAR V3 238 → 212 КБ, Light —
205 КБ (112 → 98 классов), V8 265 → 245 КБ.

Раньше сборка без `FILES` теряла «печатает» — и по исходникам было не
видно, почему. Причина нашлась: разбор способностей контакта
(`detectUserClientAndParseCaps`, TLV 0x0D/0x19 в 03/0B) сидел в том же
`#sijapp`-блоке, что и прямые соединения, и без модуля телефон не знал,
что собеседник понимает `CAP_TYPING`, — и не слал уведомления. Теперь
разбор способностей общий. В 0.83 X-статусы удалены вместе с
их настройками; хеш аватарки и «печатает» сохранены.

**Приём пакетов без лишней копии.** Раньше кадр FLAP читался в один
массив, а `Packet.parse` копировал тело SNAC во второй — на части
списка чатов (24 КБ) или истории (12 КБ) это удвоение в куче на каждый
пакет. Теперь сокет читает заголовок SNAC отдельно и тело — сразу в свой
массив, пакет кладётся в очередь уже разобранным; кадром целиком
читается только семейство 0x15 (у него свой разбор) и служебные каналы.

### Проверка производительности и памяти в 0.93

Проверены исходники интерфейса, настроек, чатов, серверной истории,
фото, аватарок, записи и воспроизведения медиа, транспорта и шифрования;
отдельно проверены результаты препроцессора и отчёты ProGuard для V3/V8.
Для сравнения использованы реальные классы 0.92 и 0.93 с заглушками
MIDP на настольной Java. Это измерения операций и выделяемых массивов,
а не скорости или свободной кучи настоящего телефона.

| Место | Было в 0.92 | Стало в 0.93 |
| --- | --- | --- |
| Переводы V3 | Все ключи в `Hashtable` | 359 числовых ключей в массиве; именованные ошибки остаются в таблице |
| Перенос слова из 900 символов | 7 829 364 символа передано измерителю ширины, 24 977 вызовов `stringWidth` | 54 262 символа, без временных подстрок для измерения |
| Пачка из 200 событий интерфейса | 200 вызовов `callSerially` | 1 вызов; порядок событий сохранён |
| Дополнительные копии JPEG | Фото: одна; аватарка: две | Нет для фото из одного пакета и аватарки |
| Неиспользуемые таймеры анимации/аватарок/звука | Три создавались при загрузке классов | Создаются при первом использовании |
| Рабочий массив SHA-256 | 64 значения `int` | 16 значений: на 192 байта меньше на хеш, на 384 байта меньше в двух хешах HMAC |
| Интересы ICQ | Таблица из 51 категории при входе | Удалена; пустая служебная часть карточки по-прежнему учитывается |

Тесты сравнивают все строки настоящего языкового пакета, 24 варианта
разбиения текста, порядок событий и следующую пачку. Фото проверяются
через настоящий BART-сокет с шифрованием и без него; заглушка декодера
проверяет исходный массив, смещение и длину JPEG. Проверяются очистка
аватарок, ошибки и нехватка памяти. SHA-256/HMAC/HKDF/ChaCha20 сверяются
с независимыми реализациями Python. Декодер V3 и фактический прирост
свободной кучи требуют проверки на телефоне.

Размер JAR почти не изменился: V3 — 217 344 → 217 370 байт (+26),
Light — 208 130 → 207 786 (−344), V8 — 247 861 → 247 482 (−379).
Основная экономия относится к объектам и временным копиям в куче;
размер архива приложения её не измеряет.

**Неиспользуемый код.** `ErrorPacket` и `PingPacket` не имели живых

нехватка памяти, 3999 переводов строки в одном сообщении, отмена и возврат

### Исправления при нехватке памяти и обрывах в 1.15

Проверки `tests/test_client_faults.py` используют настоящие классы клиента
и подставляют сбои на границах MIDP: нехватку памяти при добавлении второй
половины события, отказ `callSerially`, создание звукового плеера и отправку
пинга. Очередь сохраняет целые пары и повторяет запуск даже при заполнении;
входящие пакеты ждут освобождения лимита 16 КБ, порядок событий сохраняется.
Одна большая запись допускается в пустую очередь. Лимит относится к текстам
и массивам, а не ко всей куче или памяти нативных изображений.

Обрезанный пакет проверяется до заголовка и внутри заголовка и тела SNAC,
а также внутри другого FLAP-пакета. Для отмены открытие сокета остановлено
на барьере: отключение возвращается, а поздний сокет закрывается. Отдельно
проверены запрос без входящих данных до таймаута, потерянная побудка перед
ожиданием, позднее подключение служебного канала из старого сеанса, общий
handshake двух запросов и отказ фото при ещё работающем запросе видео.

Для настроек проверяются освобождение виджетов и отказ сохранения всей
формы при пустом или нулевом числе. Для чатов — 20 непрочитанных контактов
при лимите 12 окон, сохранение их признаков и счётчики вложенных групп.
При открытии вытесненного чата загружается последнее сообщение; более ранние
сообщения доступны в истории с сервера. Для общего списка проверены предел
20 строк, старый ответ без страниц, отмена во время разметки и PIN при
запоздавшем открытии. Загрузки проверяются с шифрованием и без него.

Аватарки декодируются рабочим потоком через тот же замок, что фото; в очереди
ожидает только последняя примета и один готовый рисунок до передачи интерфейсу.
При быстром переключении фото работает один поток и ожидает только последний
JPEG; закрытие удаляет ожидающее фото. Нативный декодер одновременно один.
Задачи освобождения аватарок и обновления
заблокированного экрана используют общий таймер. Десятисекундный таймер часов
и автоблокировки оставлен отдельным: зависшая нативная запись пинга в GPRS
не должна останавливать проверку простоя. По той же причине отдельно работает
сторож звукового плеера, закрытие которого может задержаться внутри MMAPI.

На V8 проверены запись через собственный временный файл и переименование,
сохранение существующего файла, отмена старого писателя после начала новой
загрузки и удаление только своих незавершённых частей. Записанное видео
читается из файла по 8 000 байт; обрыв исходного файла не дополняется нулями.
Подтверждения медиа проверяются по UIN, номеру операции и соединению, старые
ответы не завершают новую отправку. Отмена отложенного возврата голосового
и PIN проверены даже при принудительном выполнении уже отменённой задачи.

Мост принимает новый запрос страницы только с приметой `P1`, прежнему
клиенту возвращает прежний полный список. Корреляция частей загрузки
сохраняет запросы с нулевым номером от старых клиентов. Проверки находятся
в `tests/test_client_transport.py`; повторяющиеся строки о контакт-листе
и приметах аватарок доступны на уровне DEBUG.

### Подгрузка пустого чата и недоступные сети в 1.14

В 1.13 последнее сообщение запрашивалось только при создании окна чата.
После ошибки окно оставалось пустым, а повторное открытие уже не делало
запрос. Кроме того, запросы разных чатов имели одинаковую примету,
а успешный BART-ответ не проверялся по UIN и номеру запроса. Тест
`tests/test_client_chat_open.py` воспроизводит оба случая на классах 1.13:
после отказа остаётся один запрос, а ответ другого чата принимается.
В 1.14 повторное открытие создаёт второй запрос, чужой ответ отвергается.

Для пустого чата запоминаются только два числа `int`: запрос и сеанс.
Нет дополнительного таймера или потока. Слушатель хранит UIN и номера,
поэтому не удерживает строки закрытого чата. Ответ приходит диапазоном
исходного пакета без копии полезных данных; добавление сообщения и показ
ошибки выполняются в очереди интерфейса. Пакет освобождается после
обработки. Нехватка памяти при постановке в очередь или переносе текста
не оставляет запрос заблокированным; частичные строки очищаются, замок
перерисовки отпускается. Подгрузка сохраняет направление сообщения,
вид и примету вложения, обсуждение и ссылку цитирования.

Примета истории содержит уникальный номер в ранее неиспользуемых байтах
12–15. Поля количества, смещения и формата страницы остаются прежними.
Ответ с нулевым номером запроса от старого моста принимается при совпадении
UIN и приметы. Переподключение меняет номер сеанса: старый запрос,
убранный из очереди связи, не мешает новой попытке.

Недоступные контакты исключены из общего онлайн-счётчика и счётчиков
всех родителей дерева. Повторные статусы, добавление, удаление,
перестроение дерева и восстановление сети сохраняют точные значения.
При сортировке и скрытии таких контактов используется правило оффлайна,
а значок остаётся «невидимый». Статусы «отошёл», «недоступен», «не
беспокоить» и «занят» по-прежнему входят в онлайн-счётчик доступной сети.
Убрана попытка пересортировать отсутствующий узел при добавлении
контакта, скрытого настройкой списка.

Мост отвечает ошибкой на неудачное открытие чата из общего списка,
вместо молчания до таймаута. Ошибка MAX сохраняет причину ограничения
истории, а недоступная сеть — название сети и срок повторного подключения.
Ошибка не подменяется сообщением о пустой переписке.

В «Настройки → Сеть» добавлен выпадающий список «Пингов без ответа»,
от 1 до 10. По умолчанию 3 — фактический срок срабатывания прежнего
сторожа; старое сообщение журнала ошибочно называло два пинга. Проверка
проходит перед отправкой очередного пинга: каждый отправленный пинг,
включая последний, получает целый интервал на ответ. При интервале
120 секунд и пороге 3 обрыв определяется примерно через 6 минут после
первого пинга без ответа. Это время зависит от выбранного интервала,
а не от постоянных 120 секунд. Порог применяется на следующей проверке,
любые данные основного соединения обнуляют счётчик. При выключенном
«Поддерживать подключение?» пинги и этот сторож не работают.

Значение сохраняется новым числовым ключом RMS, без повторного
использования ключей удалённых настроек. Профили прежних версий
получают значение 3; неверное сохранённое число также заменяется на 3.
Один элемент формы и чтение настройки раз в интервал не добавляют
таймеров, потоков или периодических выделений памяти для списка.
`tests/test_client_pings.py` проверяет все десять порогов, последний
интервал ожидания, сброс по ответу, смену настройки во время работы,
старый таймер, выключенные пинги и новый сеанс. Сохранение, загрузка
старого профиля, диапазон и «Назад» проверяются настоящими Options/RMS
и OptionsForm в клиентских тестах интерфейса и навигации.

Для выпуска 1.14 прошли 69 групп клиентских проверок (23 на каждую
сборку V3, Light и V8) и 12 групп серверных проверок: шифрование,
расширенный протокол, присутствие, очистка сеансов, доставка, ресурсы,
помощники и их CLI, восстановление сетей, история MAX и eXpress.
Проверены CRC архивов, версии и размеры JAR/JAD, тексты меню, прежние
звуки и подпись V8. Размеры JAR: V3 235 374 байта (+1 988 относительно
1.13), Light 225 938 (+2 378), V8 265 588 (+2 369). Проверки клиента

### Плеер и отмена загрузки в 1.13

У плеера удалены отдельные потоки ожидания ответа, обновления времени
и поддержания подсветки. Реальные классы 1.12 и 1.13 сравниваются
в `tests/test_client_media_lifecycle.py`: при открытии голосового и запуске
воспроизведения создавались три служебных потока, теперь — ноль.
Поток записи файла и подготовки нативного плеера остаётся: эти операции
могут надолго блокировать выполнение. Размер стека KVM и экономию всей
кучи это сравнение не измеряет.

Общий таймер проверяет экран раз в секунду и ставит не больше одного
вызова в очередь интерфейса. Время голосового обновляется раз в секунду
вместо двух раз; пауза и окончание не вызывают периодическую перерисовку.
Подсветка видимого плеера подновляется раз в четыре секунды; скрытый экран
не ставит вызовы интерфейса. Ожидание первой части считается по часам,
поэтому задержка интерфейса не занижает время. При приходе частей ожидание
отменяется и не перезаписывает прогресс загрузки.

В 1.12 тест воспроизводит запуск плеера после «Назад», если его создание
задержалось. В 1.13 закрытие проверяется после создания, `realize`,
`prefetch` и `start`; устаревший или неудачно подготовленный плеер
закрывается, в том числе при нехватке памяти. Задача таймера отпускает
ссылку на экран при отмене и обрабатывает нехватку памяти при постановке
в очередь интерфейса и обновлении экрана. Повторный «Назад» не возвращает
в чат второй раз.

Временный файл получает номер открытия. Писатель частей сохраняет свой
адрес до завершения, даже если экран уже закрыт. Тесты задерживают запись,
закрывают экран, запускают новый плеер и затем продолжают старую запись:
файл нового плеера сохраняется, старый удаляется. Проверены также пауза,
повтор, перемотка, скрытый экран, отказ таймера, отказ файлового плеера
и запасное воспроизведение из памяти при отсутствии записываемого корня.
MIDP, файловая система и нативный плеер в тесте заменены заглушками;
поведение прошивки и расход всей кучи требуют проверки на физическом V3.

На стороне моста исправлена отмена запуска CLI-помощников Claude и Codex:
отмена во время подготовки каналов ввода-вывода раньше могла оставить
дочерний процесс после завершения основного. Запуск теперь сохраняется
до получения процесса, затем завершается его группа и закрываются каналы;
повторная отмена не прерывает очистку. Отдельный тест задерживает настоящую
подготовку каналов и проверяет остановку основного и дочернего процессов
при отмене, повторной отмене и таймауте. Настройки помощников не меняются.

Для 1.13 прошли по 21 группе клиентских проверок для V3, Light и V8,
а также девять групп проверок моста: шифрование, медиа-протокол, статусы,
завершение сессии, доставка/прочтение, ресурсы, оба помощника и отмена CLI.
Проверены версии и размеры JAR/JAD, целостность архивов, прежние звуки
и подпись V8. Размеры JAR: V3 — 233 386 байт (+507 к 1.12),
Light — 223 560 (+85), V8 — 263 219 (+118).

### Разбор смайлов и ссылок в 1.12

Распознавание смайлов использует исходную строку и маленькую таблицу границ
групп, собранную один раз при загрузке ресурсов. Внутри группы сначала
сравниваются первые три символа; проверка длинного остатка нужна только
подходящим вариантам. На обычном сообщении без смайлов в перенос строк
передаётся прежняя строка. Для текста со смайлами остаются только фрагменты,
необходимые для отображения. Подготовка таблиц также входит в обработчик
нехватки памяти: незагруженные смайлы оставляют обычное отображение текста.

Список URL строится при выборе действия браузера. При оформлении сообщения
и чтении истории проверяется только наличие ссылки, без коллекции адресов.
Проверка скрытой ссылки видео не выделяет строку адреса и не копирует
весь видимый текст. Адрес сохраняется отдельно, как прежде; обычные ссылки
до и после видео остаются доступны через своё действие меню.

Сравнение реальных классов 1.11 и 1.12 на настольной JVM без JIT и escape
analysis; это временные выделения памяти в разборе текста, без отрисовки:

| Проверка, 256 повторов | 1.11, байт | 1.12, байт |
| --- | ---: | ---: |

### Меньше памяти и работы для списка контактов в 1.10

При изменении контакта строка дерева ищется по числовому UIN. Раньше
для сравнения создавалась строка UIN каждого просмотренного соседа;
в большой группе это происходило заново при каждом изменении статуса.
Дополнительные поля или кэш строк для контактов не нужны.

Сортировка группы работает в существующем `Vector`, пропускает уже
упорядоченные соседние строки и сдвигает только те узлы, которые нужно
переставить. Пустые группы и листья не выделяют временный контейнер.
Для одинаковых имён и одинакового веса статуса порядок остаётся стабильным.
Узлы, выбранный контакт, вложенные группы и их счётчики сохраняются.

Цвета входящих и исходящих сообщений хранятся в маленьком массиве пар
вместо `Hashtable`, узлов таблицы и объектов `Integer`. Простому текстовому
экрану массив не нужен; повторное применение прежних цветов не выделяет
память. Смена темы перекрашивает прежние строки, новые сообщения используют
текущие цвета, а очистка текста сохраняет тему. Поддерживаются и другие
индексированные цвета.

Подсказка разблокировки без PIN запускает одну задачу существующего таймера
при нажатии клавиши. Раньше каждый кадр подсказки создавал новый `Timer`
с отдельным потоком. Повторное нажатие начинает двухсекундный срок заново;
отменённая старая задача не может погасить новую подсказку. Разблокировка,
уход в фон и начало подключения освобождают задачу. Таймер даты также
освобождается при разблокировке. Убраны ненужные копии строк состояния;
пустой экран подключения теперь принимает `null` без исключения.

### Меньше копий сообщений и объектов контактов в 1.9

Входящие сообщения читаются из исходного пакета по проверенным диапазонам.
Убраны копии внешнего тела, вложенного блока и текста, а также временные
массивы игнорируемых TLV. Идентификатор кодировки сравнивается как байты,
без временной строки. Токены вложений и ссылки цитирования по-прежнему
копируются в собственные маленькие массивы: сообщение не удерживает весь
сетевой пакет. Границы вложенных TLV проверяются относительно их блока;
повреждённое тело сообщения не получает подтверждения и не попадает в чат.

При входе ответы и список контактов также разбираются без копии всего
пакета. Для пустого списка приватности не строится таблица всех контактов
и не создаются строки UIN; при наличии записей сопоставление сохраняется.
Ник читается из диапазона, а буфер дополнительных данных создаётся
только при наличии этих данных. Сами дополнительные TLV сохраняются.
Для контакта больше не создаются два пустых 16-байтовых массива аватарки;
они выделяются, когда сервер объявил настоящую примету. После удаления
картинки из кэша готовая примета снова становится `null`, запрос доступен.
Для 97 контактов устранены 194 пустых массива. При сбросе runtime-состояния
также сбрасывается ссылка на старую картинку.

Для контакта без чата и без уведомления на блокировке не обновляется значок
заголовка: раньше это требовало поиск статуса, преобразование UIN в строку
и поиск несуществующего чата. Изображения открытых чатов и уведомления на
блокировке сохраняются. Булевы настройки используют два общих объекта
вместо отдельного `Boolean` на каждую галочку; формат RMS не меняется.

Очистка CR/NUL и восстановление CRLF возвращают исходную строку, если
изменений не требуется. Когда требуется, выделяется массив точного размера,
без растущего `StringBuffer` и промежуточных копий. Входящие URL-сообщения
теперь сохраняют токен медиа и признак входящего сообщения; ссылка видео
сохраняется для браузера. Раньше токен терялся в парсере и в чате, а такие
сообщения были отмечены как исходящие.

### Меньше памяти для чатов и текста в 1.8

Обычная строка чата или серверной истории теперь хранит первый фрагмент
напрямую. Дополнительный `Vector` создаётся только для нескольких фрагментов
в строке: например, иконки с текстом или текста с разными стилями. Раньше
даже пустая строка выделяла `Vector` с массивом на десять ссылок. В тестовой
истории из 100 сообщений по 280 символов было 1801 таких контейнеров и
18 010 ячеек массивов; теперь их нет. При удалении старого сообщения
оставшиеся строки сдвигаются одним проходом, без повторного сдвига всех
сообщений для каждой удаляемой строки. Сами строки и выделение сохраняются.

Фоновые сообщения хранят числа и признаки в одном объекте, без `Object[]`,
`Long` и двух `Integer` на каждую запись. Предел «Сообщений в чате» теперь
общий для показанных и отложенных сообщений: раньше можно было удерживать
15 + 15 при выбранном пределе 15. При открытии чата уже обработанные
исходные записи освобождаются по мере вёрстки. Подтверждение доставки,
пришедшее до открытия чата, сохраняется и затем показывает галочку;
раньше оно терялось. Токены медиа, ссылки на обсуждения и ссылки для
цитирования сохраняют привязку к сообщениям.

UTF-8 читается прямо из диапазона входного пакета и записывается в массив
точного размера. Убраны потоки, префикс длины и промежуточные копии массивов.
Исправлена обработка четырёхбайтового UTF-8, включая эмодзи: `readUTF()`
понимает другой формат Java, поэтому раньше весь такой текст мог ошибочно
считаться CP1251. Входной modified UTF-8 старого Jimm также принимается.
Для повреждённого UTF-8 сохранён выбранный запасной вариант кодировки;
неверные границы диапазона отвергаются без переполнения.

### Начальные статусы без торможения в 1.7

При подключении мост раньше отправлял статус каждого контакта отдельным
пакетом. Для каждого клиент копировал TLV, создавал массив аргументов с
числами-объектами, переставлял контакт и пересобирал видимую часть дерева.
Заголовок со счётчиком обновлялся отдельными заданиями интерфейса.

С версии 1.7 мост отправляет до 20 контактов в одном пакете, не больше
4 КиБ. Клиент передаёт исходное тело пакета в одно задание интерфейса,
читает TLV и способности прямо из него, сортирует каждую затронутую группу
один раз и пересобирает список после всей пачки. Узлы дерева сохраняются,
выделенный контакт остаётся выбранным. Счётчики родителей обновляются
вместе с дочерними группами, заголовок рисуется один раз. Подсказки о
смене статуса показываются для одиночных обновлений, но не мелькают для
каждого контакта начальной пачки. Одиночный переход между «в сети» и
«отошёл» теперь также сохраняет правильный порядок при сортировке по статусу.

На тесте реального развёрнутого дерева с 97 контактами: вместо 97
пакетов — 5, вместо 87 пересборок видимого списка — 5. Это количество
операций на настольной JVM, а не измеренная скорость Motorola. Паузы
между пачками по 0,2 секунды сохранены. При включённом `typing_prime`
новому клиенту не отправляются дополнительные фиктивные уведомления
«закончил набор»: он узнаёт поддержку «печатает» из способностей контакта.

Пачки включаются только по объявленной способности TeleMotoMax 1.7 или
новее. Старым TeleMotoMax и обычному Jimm мост отдаёт статусы как раньше.
Новый клиент понимает также одиночные ответы старого моста. Для полного
эффекта обновите и мост, и клиент; менять `config.toml` не требуется.

ActionListener, очередь интерфейса и дерево контактов. Проверяются порядок,
выделение, счётчики, аватарки, способности, время входа/простоя, скрытие

шифрование, список контактов, статусы, набор текста и закрытие соединений.

Общий рабочий буфер HMAC защищён замком только на время вычислений.
Сокеты и callbacks под этим замком не выполняются. Формат TMME/1,
проверка MAC до расшифровки и совместимость с обычным Jimm сохранены.
При медленной записи поток связи может ожидать свободного места до
15 секунд; затем загрузка завершается ошибкой. Поток интерфейса и
таймер отправки пингов продолжают работать. При отмене ожидающая часть
сразу освобождается. Если потоковая запись уже началась и прервалась,
оставшийся хвост больше не открывается как целый файл.

Голосовое в контейнере 3GP сохраняется с расширением `.3gp`, чтобы
файловый плеер не выбирал AMR и не переходил к большому буферу в памяти.
Голый AMR старого моста распознаётся по заголовку и сохраняет `.amr`.
Отказ записи уже принятого потока не закрывает общий BART-сокет:
другой запрос истории/фото может продолжиться. Некорректный ответ BART
завершает загрузку без разрыва основного соединения.

Исправлены проверка длины/порядка частей BART, обработка расширенных
флагов SNAC, переполнение при случайном выборе FLAP sequence и скрытая
ошибка записи в сокет. Ошибки одновременных запросов истории/фото/аватарок
адресуются собственному запросу; старые ответы с нулевым request ID
принимаются. При переходе с сервера входа на BOS старый поток приёмника
закрывает только свои потоки и сокет: он больше не закрывает новое
соединение, не меняет его состояние и не добавляет в его очередь старый кадр.
Для multipart-ответа `RangeListener` получает фактическую
длину без дополнительного обрезающего массива. Сборка в памяти
ограничена доступной кучей и 128 КиБ в V3/Light либо 2 МиБ в V8.

На мосте JPEG уменьшается в декодере до EXIF/RGB: тестовый снимок
24 МП загружается как 0,375 МП. Если даже минимальное качество не
вмещает фото в предел байтов, уменьшаются размеры; невозможный предел
возвращает ошибку. Все отправки MAX ограничивают таблицу подавления эха
500 записями; пересылки также учитываются. У голосовых MAX исправлен
неподдерживаемый аргумент конструктора PyMax 2.4. Кэш Blob в браузере
eXpress ограничен 30 объектами и 32 МиБ (один более крупный файл
допускается отдельно), освобождает отозванные URL и не подменяет
вложение сообщением из другого чата.

HTTP читает файлы с диска и отправляет их частями по 16 КиБ с `drain`,
без загрузки всего файла в память, копии «заголовок + весь файл» и
копирования диапазона. HEAD не открывает содержимое файла. MIME, расширение,
Content-Length, Range и HEAD сохранены. До четырёх запросов медиа или
цитирования выполняются одновременно на сессию; лишнему возвращается
читаемая ошибка, чтение пингов продолжается. Остановка закрывает также
служебные и неавторизованные сокеты, HTTP-загрузки, фоновые таймеры и отправитель.
Отмена останавливает процесс Claude с дочерними процессами и запрос
кодировщиков ffmpeg; процесс не остаётся работать после отмены.

Проверены три сборки, 14 групп тестов реальных Java-классов для каждой,
36 проверок моста и настоящее H.263/AMR-NB кодирование всех 14 настроек
V3. SHA/HMAC/HKDF/ChaCha20 проверены независимыми реализациями, включая
четыре параллельных потока с разными ключами; фото проходят настоящий
шифрованный BART-сокет и тестовые сценарии OOM/ошибки формата.

Готовые JAR 1.6: V3 — 230 287 байт (+3 665 к 1.5), Light —
221 118 (+4 050), V8 — 260 550 (+3 778). Дополнительный код ограничивает
пики памяти и исправляет ошибки; размер JAR не является замером кучи.

Это измерения на настольной JVM и сервере. Свободная куча, скорость и
совместимость нативного JPEG/MMAPI-декодера Motorola требуют проверки
на аппарате; успешный тест с заглушкой не доказывает устранение ошибки
зашифрованных фото на самом V3. Большие буферы записи голоса/видео и
воспроизведения без временного файла остаются действующими функциями.

### Серверная история в 0.94

В 0.93 каждая подгрузка сохраняла полный текст отдельно и заново
форматировала все накопленные сообщения. В 0.94 форматируется только
входящая страница; объекты старых строк и их фрагменты переносятся
без создания заново. Индексы сообщений сдвигаются вместе с метаданными,
чтобы фото, видео, голосовые, обсуждения и цитирование относились к
выбранному сообщению после любой подгрузки.

Сравнение реальных классов на настольной Java, 10 страниц по 10 сообщений:

| Измерение | 0.93 | 0.94 |
| --- | --- | --- |
| Символы, переданные измерителю ширины текста | 3 340 700 | 607 400 |
| Символы полного текста, отдельно сохранённого в истории | 30 100 | 0 |
| Повторное создание строк уже загруженных сообщений | При каждой странице | Нет |
| Хранение типа вложения | `Integer` и ссылка в `Vector` на сообщение | Один байт на сообщение, общий массив на 200 байт |

Это счётчики операций и отдельно хранимого текста, а не замер скорости
и свободной кучи V3. Проверены совпадение текста, цветов, шрифтов и
индексов с 0.93 для трёх форматов ответа, токены всех видов вложений,
скрытые адреса видео, номера цитирования и обсуждений. Проверяются
ошибки новых страниц, нехватка памяти при переносе, пустые ответы,
ограничение размера, возврат из вложенного экрана и выход во время
обработки ответа. При выходе очищаются также номера цитирования,
которые раньше оставались в закрытом объекте истории.

JAR 0.94: V3 — 217 811 байт (+441 к 0.93), Light — 208 653 (+867),
V8 — 248 830 (+1 348). Дополнительный код уменьшает выделения данных
при просмотре истории; размер JAR сам по себе не отражает эту экономию.

Ручная проверка V3 без шифрования: открылись 39 из 40 фото. При
включённом шифровании фото по-прежнему часто не открываются, в том
числе первое. Причина этой проблемы ещё не установлена; оптимизация
истории не считается её исправлением.

### V3: файловый API там другой

В прошивке V3 (P2K) файлы могут быть доступны не через JSR-75, а через
фирменный `com.motorola.io` — обозреватель файлов самого Jimm выбирает
реализацию по `Class.forName("javax.microedition.io.file.FileConnection")`
и на Motorola сваливается во второй (`res/MOTOROLA/lib/fileaccess.jar`
в classpath сборки). TeleMotoMax до 0.63 знал только JSR-75, теперь
`TempFiles` выбирает так же, и на экране ошибки видно, какой API выбран,
какие корни вернул телефон и на чём именно отказано — «no writable root»
без подробностей больше не появляется.

Заодно клип из памяти открывается не одним названием типа, а перебором
(`video/3gpp`, `video/mp4`, `video/3gpp2`, `video/mpeg4`): один и тот же
3GP телефон может взять под одним названием и отвергнуть под другим, а
мост переключается с H.263 на MPEG-4, когда кадр не QCIF.

**Доверие на V3 сменить нечем.** Дамп живого V3r показывает: корни
Java-доменов лежат файлами в `/a/mobile/certs/root/x509/kjava/`
(`motman.crt` — CN=«Manufacturer Domain 40-1», `motoper.crt`,
`mot3rd.crt`, `gt3rd.crt`; DER с двумя байтами в начале, RSA-2048,
sha1WithRSA, сроки истекли в 2018 и 2024), но какой корень к какому
домену относится, решает реестр `j2me_domain_registry.sm` рядом:
заголовок, 256-байтовое поле (размер подписи RSA-2048), записи «код
домена + DN + SHA-1 файла сертификата», имена доменов и шесть таблиц
политики. Дописать туда свой корень, не зная ключа, нечем.

`.pat`-файлов, которые описывают гайды сообщества
(`/c/mobile/kjava/j2meNN.pat`), на V3r нет: установленные мидлеты лежат
в базе `/a/mobile/kjava/J2MEST` (там видны и TeleMotoMax, и Jimm, и
SynerJ), отдельных файлов разрешений нет.

### V3: подпись проверена на телефоне — не проходит

Коротко: на V3 подписать приложение своим корнем нельзя, и это не
вопрос формата или сроков — проверено вживую.

Что сделали и что ответил телефон: корень положили в
`/a/mobile/certs/root/x509/kjava/` (DER с двумя байтами в начале, как у
заводских), перезагрузили — в общем списке сертификатов телефона он
появился; ставили подписанный JAD в двух видах цепочки (с корнем и без
него, как требует руководство V3x) и с сертификатом, действующим с
2020 года, — оба раза «ошибка авторизации, приложение не установлено».

Почему так, видно по дампу: java-домен назначает не каталог, а реестр
`j2me_domain_registry.sm` рядом. В нём у каждого заводского корня лежит
запись «код домена + DN + SHA-1 файла», и **все четыре** заводских
сертификата там есть (проверено сверкой отпечатков), а нашего — нет.
Самоподписанность роли не играет: `gt3rd.crt` тоже самоподписан и
работает, потому что он в реестре. Дописать туда свою запись нечем:
реестр начинается с 256-байтового поля размером ровно с подпись
RSA-2048, и ни с одним из открытых ключей телефона оно не совпадает.

Что остаётся на V3:

- **«Права доступа» в меню телефона**: Меню → Java (Мои приложения) →
  TeleMotoMax → Опции → «Права доступа». Это тот же набор групп, что
  гайды правят в `.pat`; если «Чтение данных» и «Запись данных» там
  переводятся в «Спрашивать», файлы откроются и без подписи;
- если нет — файлов на V3 не будет, и это терпимо: ролик и голосовое
  играются из памяти, лишь бы кусок был небольшим (предел «Видео:
  размер, КБ», у профиля v3 — 16 КБ).

Подписать V3-сборку по-прежнему можно одной командой —
`TMM_SIGN_V3=1 telemotomax/build.sh <каталог>` положит в `dist/`
`TeleMotoMax-Signed.jad` (цепочка с корнем) и
`TeleMotoMax-Signed-NoRoot.jad` (без корня), а `v3/telemotomax_root.crt`
— наш корень в формате хранилища телефона. В `dist` их не держим: на
этом телефоне они не ставятся, а в списке загрузок только путались бы.

## Две сборки: V3 и V8

`telemotomax/build.sh` собирает сборку для Motorola V3 (по умолчанию,
`TMM_MODULES=v3`) — без камеры: снимок и «кружок» из Java на V3
недоступны (`MediaException`), и пункты меню там только мешают. Сборка
`TMM_MODULES=v8 telemotomax/build.sh <каталог>` включает модуль `CAMERA`:

Файлы (JSR-75) при этом нужны и сборкам V3: плеер пишет ролик во
временный файл, из памяти V3 видео не играет. Поэтому
`Connector.file.read/write` объявлены в `MIDlet-Permissions-Opt` у всех
сборок, а не только у V8 с камерой — незаявленное разрешение телефон
вправе отказать молча, и на V3 это выглядело как «no writable root» без
причины. Телефон может спросить разрешение при первом обращении к файлам;
если в разрешениях приложения доступ к файлам стоит «запрещён» — плеер
скажет об этом в подробностях ошибки (`SecurityException`).

- **«Снять фото»** — снимок с камеры в чат; размер снимка — в настройках,
  раздел **«Камера»** (между «Прозрачностью» и «Горячими клавишами»),
  пункт «Разрешение». Список размеров берётся у самого телефона из
  `video.snapshot.encodings`, а если там одни форматы (V8 объявляет
  только `encoding=jpeg`) — из `video.encodings` (у V8 это кадры
  видеозахвата: 160×120, 120×160, 240×320, 480×640, 320×240, 480×320 —
  список есть и в `kvm` прошивки), плюс размеры фото самой камеры из
  `ezx_camera.cfg` прошивки (`photoSizeTable`, портрет): 240×320,
  480×640, 960×1280, **1200×1600** (2 МП). Именно эти пары и надо
  просить — 640×480 и 1600×1200 (ландшафт) в таблицах телефона нет.
  «Как решит телефон» — без указания размера (кадр в размер экрана,
  240×320). Неподдерживаемый размер V8 не отвергает: 640×480 давал
  «правильный» заголовок и **битый кадр** (картинка «завёрнута», низ
  зелёный — пустой YUV), 1024×768 — пустой массив; снимок без
  JPEG-заголовка не отправляется. Источник камеры по руководству
  MOTOMAGX — `capture://camera` («camera player», тип `cameraplayer` и
  класс `ViewFinderPlayer` есть в `kvm`); клиент пробует его, затем
  `capture://image`, затем `capture://video` (видеотракт: с него на V8
  больше 480×640 не снять). В журнале «Связь» после снимка видно, что
  вышло на самом деле: размер по заголовку JPEG, вес, какой источник
  открылся и что просили; мост пишет то же: «снимок с камеры → …:
  1200x1600, 180 КБ». **По документации** (Motorola «J2ME Developer
  Guide» для P2K и для MOTOMAGX) снимок — это «JPEG encoding in *video*
  snapshots»: camera player — «a special type of video player», и
  никаких параметров размера не описано; по JSR-135 просить можно только
  то, что телефон объявил в `video.snapshot.encodings`, а V8 объявляет
  лишь `encoding=jpeg` — то есть по спецификации гарантирован только
  размер по умолчанию, кадр видоискателя 240×320. На живом V8
  `capture://camera` и `capture://image` отвечают `MediaException`, типы
  захвата — `audio/x-wav, audio/amr, video/3gpp`: фото-источника у Java
  на этой прошивке нет. Что V8 принимает сверх этого, проверено на
  живом телефоне: **960×1280 — целый кадр** (291 КБ), он и стоит по
  умолчанию у сборки V8; 480×640, 640×480, 320×240 — тоже; 1200×1600
  отвергает («Invalid snapshot size»). Больше не будет: в пуле строк
  `kvm` Java-слой знает ровно три локатора — `capture://audio`,
  `capture://radio`, `capture://video` (никакого `camera`/`image`),
  слова `quality` там нет, а из движка камеры `kvm` не импортирует
  `setQuality` — качество JPEG и уровни «хорошее/лучшее» штатной камеры
  из Java недоступны. Полные 1200×1600 — штатной камерой на карту и
  «Отправить фото/видео».
- **«Записать кружок»** — видео с камеры до 30 секунд: «выбор» (или «5»)
  начинает и заканчивает запись, стоп сам на 30 с. Видоискатель — 4:3 по
  центру экрана: кадр записи у V8 4:3 (320×240), и на весь портретный
  экран телефон растягивал его в 3:4 — картинка «приближалась» при
  старте записи; полосы сверху и снизу свободны от видео, там подсказки. Запись идёт во
  временный файл (JSR-75), если есть куда, иначе в память; уходит частями
  (SNAC `10/05`, раскладка голосового) с длительностью и типом записи,
  мост перекодирует в квадратный MP4/H.264 и отправляет кружком в
  Telegram (`video_note`) или MAX (`VideoNote`). В ffmpeg моста нужен
  `libx264`, иначе уйдёт обычным видео. Ответ `10/03` — ушло или нет.

- **«Отправить файл»** — обозреватель файлов Jimm (память телефона и
  карта), выбранный файл уходит на мост частями (SNAC `10/08`) прямо из
  потока — в памяти одна часть, — и попадает в чат документом под своим
  именем. Потолок — 5 МБ в клиенте и `file_max_mb` профиля на мосте.
- **«Отправить фото/видео»** — тот же обозреватель, но `.jpg/.png` уходит
  в чат **фотографией**, `.3gp/.mp4` — **видео** (мост перекодирует 3GP в
  MP4/H.264, без `libx264` — как есть), остальное — файлом. Вид — байт
  хвостом первой части 10/08 после имени (старый мост его не читает).
  Так в чат попадают снимок 1200×1600 и ролик, снятые штатной камерой
  телефона: из Java на V8 больше 480×640 не снять, а с карты — любой.
- **«Скачать файл»** — у сообщения с документом (вид вложения 4,
  `[файл имя]`): документ приходит по службе частями (тип приметы
  `0x0086`, в первой части имя) и пишется потоком в `tmm/` на первом
  корне, куда можно писать; по концу — «Сохранено: …». Не больше
  `file_max_mb` профиля.

Про файлы на V8 (MOTOMAGX) — по «Java ME Developer Guide for MOTOMAGX»:
JSR-75 (`Connector.file.read/write`) там **Restricted API** — доступ есть
только у подписанных доверенным сертификатом приложений, «this trust
cannot be overridden by the consumer»; для неподписанных — «Not
allowed», и никакие `MIDlet-Permissions` в JAD этого не меняют (с
обязательными телефон вправе вовсе отказать в установке). Отсюда
«SecurityException: Application not authorized to access the restricted
API» на `listRoots()` — и «файл: no writable root» у плеера: ролик и
голосовое на неподписанной сборке V8 играются из памяти. Снимок и
запись — «session (oneshot)» для неподписанных, поэтому камера и
микрофон работают и без подписи.

Подписанная (см. ниже) сборка получает файлы, сеть и все остальные
API целиком — на этом фактически заканчиваются ограничения V8 по
сравнению с V3.

## Своя подпись — рабочий рецепт для V8

`telemotomax/sign.sh` подписывает сборку по JSR-118 ключами из
`telemotomax/sign-keys/` — они **тестовые** и лежат в репозитории:
корневой сертификат (`ca.der`, его — на телефон) и подписывающий (им
подписан JAR); телефон, где корень уже прописан, будет доверять любой
сборке, подписанной ими (`TMM_KEYS=<каталог>` — свои ключи, без них
`sign.sh` создаст новые). Скрипт автозапуска для телефона с этим
корнем — `telemotomax/v8/tmm_nogui.sh`. `sign.sh` дописывает в JAD
`MIDlet-Certificate-1-1/1-2` и `MIDlet-Jar-RSA-SHA1`. Разрешения в JAD не
трогает — у подписанного приложения они обязаны байт-в-байт совпадать с
манифестом внутри JAR (иначе JSR-118 905, молчаливый отказ), поэтому
нужные `MIDlet-Permissions-Opt` (файлы, камера, **и сеть** — см. ниже)
пишет сам `build.sh` в манифест при сборке.

Java-машина MOTOMAGX (`kvm`, ~2006–2008 год) по стандарту X.509 обязана
отклонять сертификат с непонятным ей **критичным** расширением — а
современный `openssl req -x509` по умолчанию ставит `BasicConstraints`
именно критичным и сам добавляет `SubjectKeyIdentifier`/
`AuthorityKeyIdentifier`, которых у заводских сертификатов Motorola нет
вовсе. Плюс срок действия сертификата в кеше телефона хранится как
**знаковое 32-битное число** — дата дальше 19 января 2038 переполняется
в отрицательную (сертификат выглядит просроченным ещё до 1970 года, и
установленное приложение отказывается запускаться с «ошибкой
аутентификации», хотя ставится нормально); заводские сертификаты
Motorola поэтому кончаются 31.12.2037, и `sign.sh` — тем же числом.
Поэтому `sign.sh` собирает оба сертификата вручную (из сырых
ASN.1-байтов через `cryptography`, не через `openssl req -x509`):
у корневого — только некритичный `BasicConstraints: CA:TRUE`, у
подписывающего — расширений нет вовсе.

**Сеть — отдельная неожиданность.** `javax.microedition.io.Connector.socket`
относится не к Restricted, а к Protected API — у неподписанного
приложения на любую сетевую операцию телефон спрашивает разрешение
диалогом. У **доверенного (подписанного)** приложения диалога уже нет, но
и разрешение runtime выдаёт только на то, что явно перечислено в
`MIDlet-Permissions`/`-Opt` — необъявленный сокет отвечает «не
разрешено» даже в домене с полными правами. Поэтому `build.sh` пишет в
манифест `Connector.socket,.http,.https` для **обеих** сборок, не только
для V8 с камерой.

**Хранилище доверия на телефоне** — не JKS/`_main.ks`, как у эталонных
Sun-овских JVM, а собственный формат Motorola: живой список доменов
лежит в `/usr/setup/.policy/_devdomain.txt` (симлинк `/usr/securesetup` —
то же самое; путь читает переменная окружения `J2ME_POLICY_DIR`),
текстом, по одному домену:

```
domain: <имя>
type: 0            # 0 производитель (Manufacturer, полные права) / 1 оператор / 2 третья сторона
rootcert: <сертификат, DER, одной строкой base64>
allowchangestatus: 0
            # запись отделяется строкой с одним пробелом
```

`/usr/setup` — squashfs, только чтение (часть образа прошивки), поэтому
правка нужна на каждую загрузку заново: `mount -o bind` поверх файла с
копией + нашим доменом. Библиотека `libezx-cmseccert.so`
(`/usr/lib/ezx/lib/`, класс `CM_SEC_DomainManager`) сама пересобирает из
этого файла **рабочий кеш** — `/ezxlocal/download/java/.policy/._policy.txt`
плюс `._hmac.txt`/`._perhmac.dat` (подписан внутренним ключом библиотеки,
руками эти три файла не редактировать — при рассинхроне с источником
кеш просто перегенерируется на следующей проверке, без перезагрузки
достаточно стереть их и заново поставить/открыть приложение).

Порядок установки на живом телефоне (по SSH/Telnet, root — есть в
SAedition, см. `find / -iname '*devdomain*'`, если версия мода другая):

```sh
# ca_b64 — вывод `openssl base64 -A < ~/.tmm-sign/ca.der`
cp /usr/setup/.policy/_devdomain.txt /ezxlocal/tmm/_devdomain.txt
cat >> /ezxlocal/tmm/_devdomain.txt <<EOF
domain: TeleMotoMax
type: 0
rootcert: $ca_b64
allowchangestatus: 0
 
EOF
mount -o bind /ezxlocal/tmm/_devdomain.txt /usr/setup/.policy/_devdomain.txt
rm -f /ezxlocal/download/java/.policy/._policy.txt \
      /ezxlocal/download/java/.policy/._hmac.txt \
      /ezxlocal/download/java/.policy/._perhmac.dat
```

Дальше — установить подписанный JAD (кеш пересоберётся сам при первой
проверке, перезагрузка не нужна). Чтобы подмена `_devdomain.txt`
пережила перезагрузку — тот же блок в скрипте `*_nogui.*`, положенном в
`/home/.autorun/` (штатный автозапуск SAedition для NoGUI-сценариев).

Проверка жизненного цикла клиента на JDK 8 после сборки:
`python3 tests/test_client_lifecycle.py /tmp/telemotomax-build` (из корня
репозитория, с рабочим каталогом, переданным `build.sh`). Проверяется
скомпилированный клиент: повторный вход, отключение до запуска потока,
выход старого потока после нового входа и задержавшиеся пинги. Интерфейс
и настройки заменены заглушками; проверка на телефоне выполняется отдельно.

**Настройки → Сеть Telegram / Сеть MAX / Сеть eXpress** (с 0.75: в 0.73–0.74 сохранение этих форм падало — номера настроек попали не в тот диапазон типов; в 0.71–0.72
был один флажок eXpress в «Учётной записи») — у каждой сети флажок «Включена»
и поле «Чатов в списке» (0 — все, пусто — как в мосте). Снятый флажок
выключает сеть на мосту (eXpress закрывает браузер, MAX и Telegram —
соединение; чаты уходят из списка), поставленный — включает обратно. Уходит
мосту парами в `01/F2`, как и «Медиа»: ключи 14/15/16 — eXpress/MAX/Telegram
(1 — включена, 2 — выключена), 13/17/18 — ограничение списка Telegram/MAX/
eXpress (65535 — все), 19 — версия клиента (major·100+minor), первой парой:
по ней мост ещё до сборки контакт-листа знает, что клиент понимает вложенные
группы. Выбор мост запоминает в базе.

**Контакт-лист деревом** (с 0.73). Мост присылает имя группы путём через `/`
(«eXpress/Групповой тест», «Telegram/Работа»), клиент строит из него дерево:
каждое звено — узел, недостающие промежуточные звенья заводятся сами,
подписывается группа последним звеном, счётчики складываются по поддереву.
С 1.5 изменения статуса, добавление и удаление контакта обновляют также
счётчики всех родителей: «Telegram», папки и группы с обсуждениями.
Связь с родителем хранится в самой группе; для обновления не нужно
перебирать контакт-лист. Как и раньше, при «Скрывать отключившихся» счётчики групп
скрыты; при нуле контактов в сети показывается только название.
Виджет дерева (`VirtualTree`) глубину умел всегда — добавился только разбор
имён. Старому клиенту мост шлёт плоские имена.

**Настройки → Медиа** — что мост отдаёт телефону, выпадающими списками
(плюс одно поле для самого телефона — «Ролик в памяти, КБ»: сколько
клипа класть в кучу, если плеер не смог взять его файлом; 0 — считать
по свободной куче, но она динамическая и скачет, поэтому число надёжнее):
фото — размер,
качество JPEG, потолок в КБ; видео — кадр, битрейт, длина, «боком»;
голосовое — битрейт (восемь режимов AMR-NB) и длина.

В 0.82 для V3 и Light доступны только кадры **128×96** и **176×144** и
битрейты **16/24/32/48/64/96/120 кбит/с**; первый пункт — «как в профиле».
В V8 списки размеров и битрейтов прежние. При обновлении V3 значение 128
кбит/с из старых настроек заменяется на 120, а неподдерживаемый кадр — на
«как в профиле». Настройки сразу уходят мосту и обновляют уже полученные
браузерные ссылки: готовое видео пересобирается по клику из сохранённого
исходника, адрес файла меняется для обхода HTTP-кеша. Во встроенном
просмотре битрейт может снижаться, чтобы уложиться в заданный предел веса
ролика; браузерный просмотр этим пределом памяти приложения не ограничен.
Первый пункт каждого списка — «как в профиле моста». Выбранное уходит
мосту парами «ключ/значение» хвостом `01/F2` — при входе и сразу при
сохранении — и на время сессии кладётся **поверх профиля** (`Bridge.tmm`:
настройки телефона → профиль → общие `[telemotomax]`); старый мост хвост
не читает. Ограничение контакт-листа — та же пара (ключ 13; «все» —
65535, потому что ноль занят под «как в профиле»): мост читает её до
того, как отдать список, так что новое число действует со следующего
входа, а не через перезапуск моста.

После входа клиент сообщает мосту платформу (`microedition.platform`),
размер экрана и кучу (SNAC `01/F2`), и мост берёт **профиль телефона**:
размер, вес и качество снимка, длину ролика, битрейт голосового, глубину
истории, ограничение контакт-листа — см.
`[telemotomax.profile.*]` в `config.example.toml`. На V3 и V8 с одним и тем
же мостом снимки приходят под свой экран.

## Расширения протокола

**Текст ключа (с 0.89).** После удаления крайних символов с кодом ≤ U+0020
(как `String.trim()` в Java) ввод должен занимать 1–64 кодовых единицы UTF-16,
как поле телефона. Ровно 64 знака `[0-9a-fA-F]` декодируются в прежние 32 байта
PSK. Для любого другого текста PSK = `SHA256("TeleMotoMax PSK v1" || 00 ||
UTF8(текст))`, где `00` — один нулевой байт; UTF-8 обычный, не modified UTF-8.
Регистр и пробелы внутри фразы сохраняются; Unicode-нормализация не применяется.
Пустой `[oscar].psk` отключает защищённый режим на мосту; пустой ключ при
включённом шифровании на клиенте вызывает ошибку. Это быстрое преобразование
не увеличивает энтропию короткой фразы. Формат TMME/1 и сессионные ключи не
меняются; 64-hex ключи совместимы с 0.88.

**TMME/1: необязательный защищённый транспорт.** Обычное приветствие FLAP
`01` с версией `1` не меняется. До учётных данных клиент отправляет FLAP
`7E`: `TMME 01`, операция `01`, 16-байтный nonce, 16 байт HMAC-SHA256
от `"client hello" || тело`. Ответ: тот же префикс, операция `02`, 32
байта случайности `os.urandom`, HMAC от `"server hello" || запрос || тело`.
Подтверждение клиента: операция `03`, HMAC от `"client finish" || запрос || ответ`.
Отказ: операция `FF`, байт причины (1 — PSK не настроен, 2 — неверный ключ,
3 — недопустимый момент/режим). Поля HMAC всегда усечены до 16 байт.

После подтверждения HKDF-SHA256 получает PSK, salt = nonce клиента + nonce
сервера, info = `TeleMotoMax secure v1`, 128 байт результата: ключ ChaCha20
клиента, ключ HMAC клиента, ключ ChaCha20 сервера, ключ HMAC сервера.
Мост посылает новое приветствие внутри защищённого потока. Дальнейшие
FLAP/SNAC остаются обычными, разбитыми на записи не длиннее 1024 байт:
`u16be длина || ciphertext || tag16`. HMAC проверяет `u64be счётчик ||
u16be длина || ciphertext` до расшифровки; счётчик отдельный для каждого
направления, с нуля, без переполнения. Nonce ChaCha20 — четыре нулевых байта
и `u64be счётчик`; начальный счётчик блока — 0. Новое TCP-соединение всегда
согласует новые ключи, в том числе дополнительная служба BART.

На V3 не требуется JCE или штатный SSL. Клиентский nonce — сохранённый
64-битный счётчик в отдельном RMS `tmm_secure_counter` и время в миллисекундах.
Он задаёт свежесть запроса, не служит источником секретного ключа;
случайность для сессионных ключей предоставляет сервер. Счётчик сохраняется
до запроса, ошибка RMS запрещает защищённый вход. Рукопожатие ограничено
45 секундами на клиенте и общим сроком авторизации на мосту. В нестандартных
сборках с модулем PROXY защищённый режим через SOCKS запрещён до входа;
все три готовые сборки используют прямые сокеты. Сброс/откат RMS
требует смены PSK. Обмен без DH не даёт forward secrecy; это собственный
транспорт базовой защиты, без независимого аудита. Браузерные ссылки вне него.

Мост узнаёт клиент по способности, пишет «клиент …: TeleMotoMax 0.1 —
расширенный протокол» и помечает сессию. Дальше только для неё:

**Доставка и прочтение (с 1.11).** После успешной отправки текстового
сообщения в сеть мост посылает обычный `04/0C`: исходный 8-байтный cookie,
`u16be` канал и UIN получателя (`u8` длина, ASCII). Отметка прочтения —
отдельный `04/16`: тот же cookie и UIN в том же формате, без поля канала.
Он отправляется только клиентам, заявившим версию TeleMotoMax 1.11 или новее.
Клиент сопоставляет отметку с исходящим сообщением по UIN и первой половине
cookie; повторная или запоздалая доставка не понижает уже полученное
прочтение. Прежние клиенты получают единственный `04/0C` по `ack_on`.

**Снимки в чате.** К сообщению с фотографией мост добавляет TLV `0x9001`
после тела (вид вложения и 16-байтный токен) — обычный Jimm дальше тела не
читает, для него это те же `[фото] подпись`. У такого сообщения в меню чата
появляется «Показать фото»: клиент просит снимок у службы `0x10` (как
аватарку, только тип приметы `0x0080` и вместо хеша — токен), мост в этот
момент скачивает его из Telegram или MAX, ужимает под `[telemotomax]`
(`photo_width`, `photo_height`, `photo_max_kb`) и отдаёт одним пакетом.
Картинка показывается на отдельном экране и живёт в памяти, пока он открыт:
«Назад» — и она отпущена (раскодированный снимок 176×176 — это ~120 КБ
кучи). Токен живёт сутки; снимок скачивается только по запросу — пометка в
тексте ничего не стоит, а сам снимок на GPRS — уже осознанный расход.
У видео тем же путём открывается кадр-превью (вид вложения 2): мост берёт
миниатюру ролика из Telegram или MAX и ужимает её как снимок.

**Выбор просмотра видео (с 0.79, все сборки).** Команда **«Смотреть видео»**
и центральная кнопка в чате или истории открывают меню **«Смотреть»** /
**«Смотреть в браузере»**. Первый пункт запрашивает ролик через OSCAR и
запускает встроенный плеер; второй открывает страницу браузера, где мост
скачивает и перекодирует видео в фоне. Пока меню открыто, видео не качается;
«Назад» возвращает в чат без загрузки. Ключ 20 в `01/F2` равен 3 — поддержка
обоих действий. Если мост не прислал ссылку, доступен только «Смотреть».
С 0.80 адрес видео исключён из общего «Открыть ссылку»: просмотр через
браузер выбирается внутри «Смотреть видео». Ссылки в самой подписи остаются.
С 0.81 вместо системного MIDP-списка используется экран `TextList` клиента
с «Назад» и «Выбрать». Открытие из истории и чата, отпускание исходной
кнопки и возврат не запускают загрузку. В истории строка со ссылкой не
считается заголовком — адрес скрывается тем же способом, что и в чате.

Подчёркнутая **[видео]** скрывает адрес страницы. После открытия браузера
страница показывает подготовку, обновляется и даёт ссылку на 3GP.
Части переключаются кнопками «Дальше» и «Назад»; их длина —
`[render] video_seconds`, 0 — целиком. `!render` не нужен; сервер `[photos]`
должен быть включён. Пароль и срок хранения те же, что для снимков.

По умолчанию ролик — H.263 176×144, 15 кадров/с, 90 кбит/с, звук AMR-NB
12.2 кбит/с (8000 Гц, моно). Профиль V8 не поворачивает его автоматически;
ручной поворот H.263 не меняет кодек и размер кадра на нестандартный.
Для совместимости с V3r мост отключает блоки `fiel` и `pasp` в контейнере
3GP: после FFmpeg разбирает готовый файл и удаляет их из описания H.263,
даже если кодировщик записал `fiel` вопреки `-field_order 0`.
Видео и звук сохраняются без повторного кодирования. Это общее исправление серверной
перекодировки для плеера и браузера; клиент и `config.toml` менять не нужно.
После обновления и перезапуска моста готовые браузерные ролики прежнего
формата будут перекодированы из сохранённых исходников при открытии ссылки.

**Видео во встроенном плеере.** Длинный ролик смотрится кусками: мост отдаёт первые
`[telemotomax] video_seconds` секунд (настройка «Видео: длина» в разделе
«Медиа», до 300 с), а команда **«Дальше»** в плеере — или клавиша «3» —
просит следующий кусок. Номер куска телефон дописывает лишним байтом за
приметой (токен вложения ровно 16 байт, спутать не с чем), мост
доматывает исходник `-ss` по ключевым кадрам и режет столько же
секунд; когда куски кончились, экран говорит «ролик кончился». Целиком
длинный ролик по GPRS ехал бы десятки минут, кусками — сразу видно
начало.

У сообщения с роликом (и в чате, и в истории) есть «Смотреть
видео»: мост в этот момент качает ролик, перекодирует первые
`[telemotomax] video_seconds` секунд тем же ffmpeg, что для `!render`
(3GP: кодек и битрейт из `[render]`, звук AMR), и отдаёт по службе `0x10`
частями до 60 КБ (тип приметы `0x0082`; во флагах примет — «часть N из
M»). Короткий ролик укладывается в один пакет — тот же путь, что у фото.
Клиент склеивает части, показывая «Загрузка видео… 2/4», и играет ролик
через MMAPI (`Manager.createPlayer` + `VideoControl` на своём экране);
«Назад» останавливает плеер и отпускает ролик. Плеер V3 не берёт видео из
памяти, поэтому ролик пишется во временный файл (JSR-75) и играет оттуда
(`file://`); из памяти — только запасной путь. Подготовка плеера идёт в
своём потоке — иначе она блокировала бы поток связи, и на время загрузки
видео замирали бы и сообщения. 10 секунд
при 90 кбит/с — около 125 КБ, на GPRS — с минуту. Если плеер телефона
откажется играть из памяти, экран так и скажет — с именем исключения.

**Снимок с камеры.** В меню чата — «Снять фото»: открывается видоискатель,
кнопка «выбор» (или «5») делает снимок, и он уходит прямо в этот чат —
частями по 30 КБ на основном соединении (SNAC 10/02: кому, номер части,
сколько всего, кусок), мост собирает и отправляет его в Telegram или MAX и
отвечает 10/03 — ушло или нет. По «ушло» экран закрывается сам. Обычный Jimm
таких пакетов не шлёт, а мост принимает их только от расширенной сессии.
Камера и отправка работают в своих потоках, поток связи не занят.

**Голосовые.** У сообщения с голосовым (и в чате, и в истории) есть
«Прослушать»: мост качает запись, перекодирует её в AMR в контейнере 3GP —
тот единственный звук, который V3 умеет, — и отдаёт по службе `0x10` так же
частями, как ролик (тип приметы `0x0083`). Клиент пишет её во временный
файл и играет; «Назад» останавливает плеер и отпускает запись. Битрейт —
настройка `[telemotomax] voice_kbps`: AMR-NB знает восемь режимов
(4.75 … 12.2 кбит/с), заданное округляется к ближайшему. На 12.2 это
около 1.5 КБ в секунду, на 4.75 — втрое меньше, и по GPRS заметно
быстрее.

Экран проигрывания показывает, что происходит: «Играет / Пауза /
Проиграно», время («0:03 / 0:12») и полосу, если плеер знает длительность.
«Выбор» (или «5») ставит паузу и снимает её, в конце — играет ещё раз; «4»
(или влево) — с начала; «0» или «Назад» — закрыть.

Своё голосовое пишется из меню чата по «Записать голосовое»: «выбор» (или
«5») начинает запись, он же её заканчивает, на экране бегут секунды.
Телефон пишет микрофоном через `capture://audio` (`RecordControl`), запись
обрывается сама на 60 секундах или на 512 КБ (а `[telemotomax]
voice_seconds` — потолок длительности при перекодировании, в обе стороны). Дальше — как со снимком: части по 30 КБ на основном
соединении (SNAC 10/04: кому, номер части, сколько всего, длительность,
кусок; хвостом первой части — тип записи, например `audio/amr`), мост
перекодирует AMR в OGG/Opus и отправляет в Telegram или MAX именно
голосовым сообщением, а не файлом, и отвечает 10/03. **Для этого ffmpeg
на мосте должен уметь opus** (Gentoo: `USE="opus"` у `media-video/ffmpeg`;
без него в журнале будет «нет ни libopus, ни libvorbis» и запись уйдёт
вложением `voice.amr`). Запись и отправка идут в своих потоках.

**Все чаты.** Контакт-лист телефона обрезан `roster_limit`, и чат, в
который давно не писали, из него выпадает — написать в него с телефона
становится нечем. Поэтому в главном меню вместо «X-статус» (с мостом его
всё равно нет) стоит «Контакты»: управление контакт-листом, которое в
Jimm лежало в настройках, и первым пунктом — «Все чаты». Сам
контакт-лист в меню зовётся «Чаты» — так видно, где отфильтрованный
список, а где всё, что знает мост: мост отдаёт по службе `0x10` (тип приметы
`0x0084`) весь свой список — UIN, флаги (в MAX ли чат или в eXpress, есть
ли он в контакт-листе), сколько дней там тихо и название. Экран показывает его
списком: «[T] Мама, 3 дн.», «[M] Таня, 40 дн.», «[E] Коллега, сегодня». Выбор чата просит мост
вернуть его на телефон (тип `0x0085`): мост снимает скрытие, поднимает
чат в начало списка и присылает последнее сообщение переписки — после
этого чат виден в клиенте и в него можно писать.

Обычный Jimm этой службы не знает, но и ему есть чем: пустая форма
«Поиск пользователя» (или «\*» в любом поле) теперь означает «покажи
всё» — мост отдаёт список чатов выдачей поиска, по одной карточке на
экран, с теми же пометками `[T]`, `[M]` и `[E]` в имени.

**Видео не проигрывается.** MMAPI на V3 знает из семейства 3gpp только
`audio/3gpp` — видео там не поддержано вовсе, и ролик из программы не
сыграть (проверено на телефоне 2026-09-16: «плеер: audio/3gpp»). Поэтому у
видео остаётся только кадр-превью. Звук при этом поддержан
(`supports.audio.capture` = true) — голосовые и играются, и пишутся.

**История с сервера.** В меню чата — «История с сервера»: последние N
сообщений (Настройки → Чат → «Сообщений в истории с сервера», по умолчанию
10) приходят по той же службе `0x10` (тип приметы `0x0081`, число
сообщений — в первых двух байтах «хеша») и показываются на отдельном экране,
по одному пункту на сообщение. Запись от моста — длина текста, UTF-8, флаг
и, если у сообщения есть фото, его токен: у такого пункта работает то же
«Показать фото». Разбор и вёрстка истории, как и показ фото и подготовка
плеера, идут в отдельном потоке: ответы службы приходят в поток связи, и
тяжёлая работа в нём остановила бы обмен сообщениями. В отличие от `!last`,
который сыплет историю в саму переписку, где она остаётся до закрытия чата,
этот экран уносит весь текст с собой по «Назад». Мост отдаёт не больше
12 КБ за раз.

История приходит пачками: сколько сообщений в пачке — в настройках
(«Сообщений в истории с сервера», по умолчанию 10), а пункт «Ещё» в
правом меню экрана просит следующую, старее показанных. Там же лежат
«Показать фото», «Смотреть видео» и «Прослушать» для записи, на которой
стоит курсор; выбор записи открывает вложение сразу. Под сообщением, с
которого в eXpress начато обсуждение, в меню есть «Обсуждение» (с 0.74; в 0.72–0.73 ответ с такой записью клиент отвергал):
открывается история самого обсуждения, поверх текущей, «Назад» возвращает.
Мост помечает такую запись битом 0x10 флага и дописывает за токеном UIN
обсуждения (4 байта) — только клиенту 0.74 и новее, старый этот бит не
разберёт. В запросе мост получает и сдвиг (сколько
телефон уже показал), и в ответе первым байтом говорит, осталось ли что
листать — когда не осталось, «Ещё» пропадает. Всего за один заход можно
пролистать `[telemotomax] history_max` сообщений (200), на экране держим
не больше 200 строк. Свои сообщения в истории помечены флагом записи: имя и время красятся
как в чате (свои одним цветом, чужие другим), а текст идёт со следующей
строки обычным цветом и тем же выводом, что и сообщения в переписке —
со смайлами. Перевод строки между ними обязателен: без него текст
дописывается в строку заголовка, и то, что в неё не влезло, уходит за
край экрана. Ответ моста клиент читает
независимо от его возраста: со страницами впереди идёт примета `0xFF` и
байт «есть ещё», у мостов постарше её нет, и начало подбирается по
тому, ложатся ли записи ровно до конца ответа.

Ошибка загрузки возвращается SNAC `10/01`, а не пустой пачкой `10/07`.
После двухбайтного кода мост может добавить TLV `0x9003` с причиной в UTF-8;
клиент 0.86 показывает её в окне ошибки. Без этого TLV работает обычная
ошибка старого протокола. Неудачная подгрузка не меняет число показанных
сообщений и не означает конец истории: «Ещё» позволяет повторить запрос.

**Чат открывается всегда.** Выбор контакта в списке открывает его чат, даже
если сообщений ещё не было (в Jimm показывалось меню контакта — оно теперь
пунктом меню чата). Пустой чат сам просит у моста последнее сообщение
переписки и кладёт его в окно — с токеном фото, если оно там есть.

## Настройки на телефоне

Шрифт: в Jimm 0.6 шрифты системные, мельче системного «мелкого» не бывает.
Мелкий выбирается в «Интерфейс → Мелкий шрифт» (контакт-лист) и
«Сообщения → Мелкий шрифт» (чат, по умолчанию включён).

«Интерфейс → PIN блокировки» принимает 4–8 цифр, включая начальные нули.
Пустое поле выключает PIN. Для выхода из блокировки удерживайте `#`,
введите PIN и нажмите `#` ещё раз. `*` стирает цифру, правая софт-клавиша
возвращает на экран блокировки. При неверном PIN ввод очищается, можно
повторить попытку. PIN хранится в настройках телефона и мосту не передаётся.

«Интерфейс → Автоблокировка, мин» задаёт время без нажатий клавиш до
блокировки приложения: по умолчанию 2 минуты, 0 — выключена, максимум
999 минут. Проверка выполняется раз в 10 секунд, поэтому блокировка
может произойти немного позже выбранного срока. В редакторе сообщения,
формах настроек, окнах ошибок, при подключении и на экранах фото, видео,
записи или скачивания она не срабатывает. Возврат из этих экранов или
разблокировка запускает полный интервал заново. Это отсчёт активности
приложения, а не определение физического состояния подсветки.

«Оповещения» отдельно настраивают звук сообщений в обычном режиме и при
блокировке приложения. С 0.97 режим и мелодия выбираются одним списком:
«Нет», «Писк», `message.mp3`, `msg_low.mp3`, `tg.mp3`, `typing.mp3`.
Выбор файла включает его воспроизведение, громкость задаётся отдельно.
Сохранённое ранее другое имя файла остаётся дополнительным пунктом списка,
пока не выбрана другая мелодия. Общий беззвучный режим действует на оба
профиля. Блокировка здесь — блокировка клавиатуры внутри приложения.

С 1.0 в этой же форме два независимых списка вибрации: для обычного режима
и блокировки, рядом с соответствующим звуком и громкостью. В каждом —
«Нет», 0,1 / 0,2 / 0,5 / 1 / 1,5 / 2 секунды; общий переключатель
условий удалён. По умолчанию оба выключены. При обновлении «Нет» выключает
оба профиля, «Да» сохраняет длительность каждого, «Если заблокирован»
включает только профиль блокировки. Прежнее «Если не трогали 60 с» также
переносится в вибрацию при блокировке. Если в старой версии длительности
ещё не задавались, для включённого профиля используется 0,5 секунды.
С 1.1 неработающий на V3 вариант 0,05 с удалён; если он был выбран в 1.0,
при обновлении соответствующий профиль получает 0,1 с.

`tg.mp3` — [штатный звук сообщения Telegram Desktop](https://github.com/telegramdesktop/tdesktop/blob/fd24aff6b15915310e3d38ddacf8e4e3d4fb30bc/Telegram/Resources/sounds/msg_incoming.mp3),
перекодированный в тот же формат, что остальные мелодии Motorola: MP3,
моно, 22050 Гц, 32 кбит/с, без ID3 и Xing. Оригинал, лицензия GPL-3.0-or-later
и команда конвертации находятся в `third_party/telegram-sound/`.
`msg_low.mp3` сделан из неизменённого `message.mp3` с уменьшением амплитуды
в двадцать раз перед кодированием; воспринимаемая громкость зависит от телефона.
